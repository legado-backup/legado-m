## 二、发现的问题（深度反思）

### 问题1：AGENTS.md 迁移不彻底（5个空壳段落）

**现状**：AGENTS.md 还保留5个"已迁移"空壳段落：
- L127-130 复杂任务处理流程（已迁移）
- L134-137 输出与工具预算管理（已迁移）
- L241-244 OpenSpec工作流程（已迁移）
- L248-257 上下文压缩恢复（由全局管理）
- L395-397 并发文件修改规范（已迁移）

**影响**：
- 这些空壳让 AGENTS.md 看起来臃肿（用户觉得"还在项目主规范中"）
- 与 L9-25 的"全局规范引用索引"重复
- 用户引用旧版行号时，可能看到这些空壳认为没迁移

**整改方案**：彻底删除5个空壳段落，只保留 L9-25 的统一引用索引

### 问题2：全局规范文件质量参差（openspec-workflow.md 严重过简）

**现状对比**：
- 全局 openspec-workflow.md：52行，2.6KB
- 项目 openspec-workflow.md：389行，详细版

**丢失的关键内容**：
- 四文档的详细结构要求（spec.md 必须包含的5个子章节）
- ADR Y-Statement 模板
- 文档同步映射表（步骤8详解）
- 上下文预算检查机制
- 正确示例 vs 错误示例
- 文档状态流转
- AI Agent 检查清单

**影响**：其他项目的 AI 加载全局版时，缺少关键细节，可能执行不到位

**整改方案**：补充全局版关键内容，在注入配额内尽量完整

### 问题3：核心问题"其他项目不加载/不遵守"未真正解决

**用户原话**："我在其他项目中，你不会主动使用AskUserQuestion工具询问我的意见，又私自自动就中断任务了"

**可能原因分析**：

| 原因 | 可能性 | 说明 |
|------|--------|------|
| 全局规范未被注入 | 中 | 11个文件合计约24KB，可能超注入限制（12KB） |
| 注入了但被截断 | 高 | 核心5文件9.42KB在限制内，但rule可能在截断边界 |
| 注入了AI不遵守 | 中 | 规范强制力不够，或被其他内容淹没 |
| 系统注入机制问题 | 低 | 可能只注入部分文件 |

**关键疑点**：
- 上一会话只在本项目（legado）验证，未验证其他项目
- 子代理验证看到的是旧状态（系统注入时机固定）
- 用户反馈"其他项目不遵守"，说明问题确实存在

**整改方案**：
1. 确认系统注入机制（文件数量/大小限制）
2. 确保 rule-1782963384927.md 优先注入（修改时间最早）
3. 增强规范强制力（在 user_rules.md 添加"每次对话必须遵守"入口）

### 问题4：可能还有通用内容可迁移

**候选1：改造过程日志记录的通用原则**
- 通用部分："改造必加日志"+"日志覆盖错误分支"+"永久/临时双轨"

- 整改：通用原则迁移到全局，项目特定场景保留

**候选2：版本交付同步的通用原则**
- 通用部分："代码变更后必须同步更新日志"
- 项目特定部分：updateLog.md 的具体格式
- 整改：通用原则可迁移，但优先级低

**候选3：子规范强制加载机制**

- 这个表是通用的（OpenSpec/代码变更/复杂任务/E2E/书源）
- 但具体子规范路径是项目特定的
- 整改：通用机制迁移，项目特定路径保留

### 问题5：规范强制力需增强

**现状**：
- user_rules.md L26-42 的"压缩恢复驱动规则"只在压缩恢复时触发

**整改方案**：
- 在 user_rules.md 添加"每次对话开始必须确认已加载全局规范"的入口
- 或者让 rule-1782963384927.md 更加自包含（不依赖其他文件）
