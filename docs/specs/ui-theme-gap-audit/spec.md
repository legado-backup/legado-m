# ui-theme-gap-audit 需求规格

## Intent

终结 App 前端"三态并存"导致的子页面多风格问题。**第一**，通过静态代码审计识别全部"未被主题设置 / 界面设置设置项管理到的子页面、组件、弹框"，输出带源码定位与修复建议的结构化问题清单。**第二**，基于静态分析结论与 `frontend-ui-standards.md` 强制基线，编写可直接对接 `ai_tests`（模拟器 uiautomator2 自动化 + 本地 Qwen3VL-8B 多模态图片分析）的全量样式测试用例，作为后续"一次测全量 → 整理完整问题清单与解决方案 → 一次修复 → 第二轮/第三轮复测"的依据。

关键约束（用户明确要求）：**禁止测出一个问题就改一处再重测**，必须全量测试、全量清点、一次修复、再进入复测轮。

## Scope

### In Scope（本条）

1. **全量页面清点与覆盖**（用户强制要求"全面"）：以 `AndroidManifest.xml` 为唯一事实源清点**全部 Activity**，连同**全部 Fragment / 弹框 / 底部弹层 / 子面板**（含 View 弹框、PopupMenu、ComposeDialog 家族、AppModalBottomSheet），生成**页面覆盖矩阵**（页面 × 样式维度），审计与测试**均按矩阵逐格覆盖，禁止抽样/按骨架×族代替全量**。
2. 全 App 前端 UI 静态审计：`app/src/main/java/io/legado/app/ui/**`（Activity/Fragment/Compose 页面/组件/widget）+ `res/layout/**` + `res/drawable/**` + `res/values/**` 中影响样式的声明。
3. 主题管理面定义（7 类设置项）与"未被管理"判据矩阵 C1-C6。
4. **处置前后预期效果覆盖**：每个测试点必须含"处置前基线（before）→ 处置（设置项变更/经典·新版切换/日夜切换/布局切换）→ 处置后生效（after）"三段式记录与断言，保证"设置项改了什么、哪里应跟着变、实际变没变"可对账。
5. 结构化问题清单 v0：页面/组件 → 缺口类型 → 源码定位（文件+行锚点）→ 影响 → **修复方案** → 优先级（P0/P1/P2）。问题清单的**核心是"发现问题→定位到代码问题→给出可执行解决方案"**。
6. 测试用例集 `ai_tests/cases/F-UI-THEME/`（MD 轨道 case.md，可被 `run_e2e.py --tc F-UI-THEME` 筛选加载）。
7. 多模态判定协议（system prompt 模板 + `chat_json` 输出 Schema + 采样校准），及 VL 分析脚本骨架。
8. 轮次协议（R1 全量 → 清单 → 一次修复 → R2/R3 复测）与门禁。

### Out of Scope（不在本条）

- **不做源码修复**：修复是下一轮工作，以问题清单 v1 为准、逐项经用户确认后实施。
- **不整体迁移 Archive UI**：`archive-ui-migration-202608` 独立进行（设计期），本任务只对齐其已落地部分（ui/config 主题体系）。
- **阅读器内核（S5 View 红线）**：禁止迁移/改动，仅审计其弹层与浮层样式是否被管理。
- **数据库 / 网络 / 功能逻辑类测试**：既有 ai\_tests 用例集不动，本任务只新增样式维度。
- **构建 / 打包 / 性能**。

## Approach

### Selected Approach：判据驱动静态审计 + 既有基建对接的用例设计（五步法）

1. **定义主题管理面**：整理 7 类设置项 → 设置项 key → 消费组件/API 映射（管理面基线文档），作为"被管理"的判定基准。
2. **静态判据矩阵扫描**：C1-C6 对应 Grep 模式集 + 脚本聚合（详见 design.md），产出原始命中清单（文件+行号）。
3. **人工/子代理核验**：按页面分组，排除合理例外（封面主色、阅读正文可配置色、品牌强调色等），收敛为问题清单 v0。
4. **用例设计**：按 `frontend-ui-standards.md` 的 S1-S6 骨架 × 组件六族展开；每个用例含前置、步骤、预期（样式断言点，标注"VL 判定 / 元素断言 / 主题联动"三种验证法）。
5. **对接执行链**：用例落 `ai_tests/cases/F-UI-THEME/case.md`（沿现有 F-P0-6 格式）；VL 判定走 `LlmClient.chat_json`；产出 `ui_visual_verify.py` 骨架。

### Alternatives Considered

| 方案                         | 否决/接受理由                                                                                         |
| -------------------------- | ----------------------------------------------------------------------------------------------- |
| A. 整体迁移 Archive UI 层（一劳永逸） | **否决**：archive-ui-migration-202608 尚在设计期，成本高、周期长；用户本轮诉求是"先清点缺口 + 建测试能力"，不是重做 UI。                |
| B. 边测边修、边修边测（小步快跑）         | **否决**：用户明确要求"不要测出来一个问题就优化再编译再测试"，必须一次测全量、一次修复，避免反复打断与回归污染。                                     |
| C. 仅静态审计、不写测试用例            | **否决**："静态分析不出的运行时问题"（设置项中改后是否真的联动、经典/新版切换是否留残留标签）无法覆盖；无图片证据无法说服用户。                             |
| D. 自研独立视觉校验工具（截图与 AI 分析分离） | **否决**：`ai_tests` 已有 LlmClient（chat\_with\_images/chat\_json）+ Qwen3VL-8B 全链路，直接复用，新增连接/维护成本为零。 |
| E. 逐页人工截图肉眼判读              | **否决**：不可规模化、无法回归、主观偏差大；仅作为 VL 判定的抽样校准手段（对账用），不作为主通道。                                           |

### Drawbacks（选定方案已知缺点 + 接受理由）

| 缺点                                        | 程度 | 接受理由 / 缓解                                                     |
| ----------------------------------------- | -- | ------------------------------------------------------------- |
| 静态判据有误报/漏报（硬编码色可能是合理品牌色）                  | 中  | 判据扫描只做"候选池"，全部经页面归属核验；误报率靠 C1-C6 与"合理例外清单"压降。                 |
| VL 对颜色/圆角/小字号的判定受降采样（最长边 640）与模型精度影响有不确定性 | 中  | 协议强制：页面全图 + 局部放大双截图送审 + `chat_json` 带置信度 + 抽样人工复核（对账差值收敛才通过）。 |
| 一次修复面大，回归风险高                              | 高  | 轮次协议内置：R2 复测必须全量重跑；R3 终测 + 关键交互（主题联动/经典切换）专项回归。               |
| 测试用例多、用例书写成本高                             | 中  | 用例按骨架×族矩阵组织，公共前置（导航/设色）抽为共享步骤，避免逐页重复描述。                       |

## Requirements

### 功能需求

- **FR-1 管理面基线**：输出"7 类设置项 → key → 消费组件"映射表，覆盖 ThemeStore/ThemeConfig、TopBarConfig、PreferKey（主色/圆角/字号/背景/沉浸/栏阴影/搜索框）、AppShapes/UiCorner、字体刻度表。
- **FR-2 全量页面覆盖**（用户强制）：先产出**页面覆盖矩阵**——Manifest 全部 Activity（100%）+ 全部 Fragment + 全部弹框/弹层/子面板清单；审计逐 Activity/Fragment/弹框覆盖，**覆盖率 = 已审页面 / 全量页面，交付物必须附覆盖矩阵核对表**（含无法触达页面及原因登记）。
- **FR-3 问题清单 v0**：每条含——页面/组件 ID、缺口类型（C1-C6）、源码定位（文件+行锚点）、运行影响、**修复方案（可执行，含改动文件与要点）**、优先级 P0/P1/P2。
- **FR-4 测试用例集**：`ai_tests/cases/F-UI-THEME/case.md`，TC-ID 规则 `TC-F-UI-THEME-xx`；**按页面覆盖矩阵逐页建用例**（不漏页），每页含：样式呈现（\[VL]/\[UI]）、主题联动（\[联动]）、处置前后对照（before/after 断言）；覆盖 S1-S6 骨架 × 六族组件 × 经典/新版切换 × 夜间/墨水屏 × 空态。
- **FR-5 VL 判定协议**：system prompt 模板 + `chat_json` 输出 Schema（observations + issues 数组含 match/confidence）+ 三图采样（页面全图 / 局部放大 / **处置前后对照**）+ 抽样校准标准。
- **FR-6 轮次协议**：R1 全量（`--tc F-UI-THEME` 全量页面批次）→ 清单 v1 → 用户确认 → 一次修复 → R2 复测 → R3 终测；门禁：R2 fail=0 才可进入修复收尾。
- **FR-7 处置前后覆盖**：所有设置项变更（主色/顶栏/圆角/字号/背景/沉浸/夜间）与模式切换（经典↔新版、日夜、布局 switchLayout）的用例，必须记录 before 基线与 after 生效结果，用于"设置项 → 生效范围"对账，直接暴露"改了不生效/半生效"类问题。

### 非功能需求

- **NFR-1** 判据可重复执行：扫描模式集固化为一处（脚本或文档），重跑结果稳定。
- **NFR-2** 用例可加载：`run_e2e.py --tc F-UI-THEME` 可筛选执行，不破坏既有用例。
- **NFR-3 输出安全**：问题清单/报告禁止输出源名称、域名、完整 URL、cookie 等（遵守 `output-safety.md`）；VL prompt 不含业务数据。
- **NFR-4** 本轮不改任何 `app/src` 源码（除允许的测试脚本外），保证"审计不改代码"。

## Scenarios

- **S-1 主题联动**：在主题设置改主色 → 全体页面头部/按钮/标签/进度条即时联动；夜间模式改日间色提示"已保存，切换后生效"不误。
- **S-2 顶栏管理**：顶栏管理改标签栏色/选中色/壁纸 → 书架/订阅/发现/阅读记录/我的五主界面头部全生效（对齐 ADR-01 局部读配色结论）。
- **S-3 右上角菜单统一**：全 App 三点菜单均为 `ModernActionPopup` 一族，无残留 `PopupMenu`/自定义 View 菜单。
- **S-4 弹框族统一**：帮助/日志/编辑/单选/确认/分组管理均走 `ComposeDialog` 家族（AppDialogFrame），无残留 View 弹框（`dialog-*` XML）。
- **S-5 经典/新版切换**：订阅页经典↔新版切换后头部标签无残留（回归 bugfix-20260824 ⑤），结构性问题（如 `modernRssPage` 无消费方）清点入册。
- **S-6 夜间/日间即时生效**：`ThemeSync`/RECREATE 覆盖的页面清单与盖不着的页面清单（审计产出）对账。
- **S-7 墨水屏**：E-Ink 模式下强制黑白 + 透明导航栏行为一致。
- **S-8 搜索框口径**：全 App 搜索框 18dp 圆角浅底统一（回归 bugfix ②），Compose/View 两端一致。
- **S-9 空态/骨架屏**：无数据时的 EmptyStatePlaceholder / 骨架屏配色跟随主题。
- **S-10 全量覆盖核对**：交付时附"页面覆盖矩阵核对表"——Manifest 全 Activity 逐一标记：已审计 / 已建用例 / 运行时无法触达（登记原因，如需要真实数据/付费/登录）。用户可据此核验"是否真的全面"。
- **S-11 处置前后对账**：任取一个设置项（如改主色）→ 记录 before（全部受影响页面基线）→ 处置 → 记录 after → 对账"预期应变的页面 vs 实际变的页面"，差额即"改了不生效"缺口（P0 类）。
