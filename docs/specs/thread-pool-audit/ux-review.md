# 线程池审查报告 - 产品UX审查

> 审查对象：`docs/specs/thread-pool-audit/audit-report.md`（35 项优化建议）
> 审查视角：产品用户体验（非技术正确性）
> 审查日期：2026-07-25

---

## 一、整体评估

### 1.1 UX 评分：6/10

**评分依据**：
- 技术深度充分（13 配置点 7 维度全覆盖），但缺乏用户视角的收益量化
- 35 项建议中仅约 10 项有明确用户可感知收益，其余偏工程自嗨
- 默认值合理性章节未给出按设备分级方案，对低端机型 UX 保护不足
- 缺少面向用户的 updateLog 沟通建议，用户无法感知优化价值

### 1.2 关键发现（5 条）

1. **用户可感知收益缺量化**：6 项 P0 中 0 项给出量化收益（如启动时间减少 X ms、崩溃率降低 Y%），用户无法判断优化价值
2. **P0-6（Coroutine.async scope 改造）属典型过度设计**：影响 50+ 调用点、回归风险高、用户无感知，应降级
3. **P1-2（threadCount 改 var）应升级 P0**：用户调整配置后不生效是真实 UX 痛点，但被定为 P1
4. **P1-10（启动期任务并行化）应升级 P0**：启动速度是用户最直接痛点，但被定为 P1
5. **低端机型保护缺失**：searchThreadCount=32 在 8 业务池叠加可达 256+ 线程，低端机型 OOM 风险高，但默认值未按设备分级

## 二、P0 优化建议 UX 评估表

| 编号 | 建议 | 用户感知度 | 量化收益 | 过度设计风险 | UX 优先级调整建议 |
|------|------|-----------|---------|-------------|-----------------|
| **P0-1** | 拆分 upTocPool 与 cacheBookPool | 低（级联失败少见） | 无 | 低 | **保持 P0**（崩溃风险） |
| **P0-2** | upTocPool @Volatile 保护 | 无（并发可见性） | 无 | 低 | **降级 P1**（纯工程正确性，用户无感知） |
| **P0-3** | CacheBookService 关闭顺序 | 中（退出崩溃） | 无 | 低 | **保持 P0**（用户可感知崩溃） |
| **P0-4** | CheckSourceService Flow 改造 | 高（校验卡死） | 无 | 低 | **保持 P0**（用户操作直接卡死） |
| **P0-5** | API Controller apiPool 隔离 | 中（API 风暴卡顿） | 无 | **中**（无实际投诉证据） | **降级 P1**（场景少见，建议先收集证据） |
| **P0-6** | Coroutine.async 移除 MainScope | 无（协程泄漏累积） | 无 | **高**（50+ 调用点，回归风险极高） | **降级 P1**（成本与收益严重不匹配） |

**P0 评估小结**：
- 6 项 P0 中仅 P0-3、P0-4 用户能直接感知（崩溃/卡死）

- P0-5/P0-6 缺乏实际用户投诉证据，属于"理论上可能出问题"的预防性改造，成本高、回归风险大

## 四、过度设计清单

### 4.1 严重过度设计（建议降级或暂缓）

| 编号 | 建议 | 过度设计理由 | 处置建议 |
|------|------|-------------|---------|
| **P0-6** | Coroutine.async 移除 MainScope | 影响 50+ 调用点，回归风险极高；审查报告自身标注"建议单独立项"；用户零感知；无实际协程泄漏投诉证据 | **降级 P1**，需先收集泄漏证据再决策 |
| **P0-5** | API Controller apiPool 隔离 | 新增 FixedThreadPool(8) 增加资源开销；API Controller 由 Web API 触发，普通用户不会高频调用；"64 线程耗尽"为理论推演 | **降级 P1**，先做运行时验证确认是否真耗尽 |
| **P1-13** | globalExecutor 任务拆分 | Bitmap 回收与日志 I/O 反压为理论风险，审查报告未给出实际反压证据；拆分后增加复杂度 | **降级 P2** |
| **P1-14** | globalExecutor 有界队列 | 无界队列 OOM 为极端场景，单线程池任务量本身有限 | **降级 P2** |
| **P1-6/7/8** | DispatchersMonitor 3 项 | 监控组件仅 `recordLog=true` 时启用，普通用户不会开启；3 项优化可合并为 1 项 | **降级 P2 并合并** |
| **P2-9** | ContentTextView 单线程池合并评估 | 收益不明显，合并后可能引入新问题 | **删除或保持 P2 不动** |

### 4.2 可合并简化项

- **P0-4 与 P1-16**：均涉及 CheckSourceService/CheckRssSourceService 的 runBlocking 改造，应合并为 1 项
- **P1-1 与 P2-4**：ThreadFactory 命名与抽取公共 ThreadFactory 工具类，应合并为 1 项
- **P1-3 与 P1-4**：异常路径 close() 与 stopSearch() 后置 null，属同类问题，应合并
- **P2-10/P2-11/P2-8**：globalExecutor 3 项 P2 优化（命名/shutdown/文档化），应合并为 1 项

## 六、用户沟通建议

### 6.1 updateLog.md 应包含的优化条目（面向用户语言）

| 技术项 | 面向用户的 updateLog 条目 |
|--------|-------------------------|
| P0-3 | 修复缓存下载完成后退出应用时可能崩溃的问题 |
| P0-4 + P1-16 | 修复书源校验过程中可能卡死不动的问题 |
| P0-1 | 提升目录更新与缓存下载的稳定性，避免相互影响 |
| P1-2 升级 | 修复线程数配置修改后不立即生效，需重启应用的问题 |
| P1-9 升级 | 优化低端机型大并发场景下的内存占用，降低崩溃风险 |
| P1-10 升级 | 优化应用启动速度，减少启动等待时间 |
| P1-15 升级 | 优化移动网络下的连接复用，减少偶发网络卡顿 |

**不应进入 updateLog 的项**（用户无感知）：
- P0-2（@Volatile）、P1-1（ThreadFactory 命名）、P1-11/P1-12（日志）、所有 DispatchersMonitor 优化、所有 globalExecutor 优化

### 6.2 是否需要新增用户可见配置入口

**建议新增**：性能模式开关（低端 / 标准 / 高性能 三档）

| 模式 | searchThreadCount | updateCacheThreadCount | 适用机型 |
|------|-------------------|------------------------|---------|
| 低端 | 8 | 4 | ≤4GB RAM / ≤4 核 |
| 标准（默认） | 16 | 8 | 4-8GB RAM / 6-8 核 |
| 高性能 | 32 | 16 | ≥8GB RAM / ≥8 核 |

**理由**：
- 当前 searchThreadCount=32 对低端机型过激进，但用户不知如何调整
- 三档开关比技术参数（线程数）更友好，用户无需理解线程池概念
- 内部自动映射到 totalBusinessThreadCap，避免用户面对技术细节

**不建议暴露给用户的配置**：
- totalBusinessThreadCap（全局上限）- 内部保护机制
- OkHttp keepAliveDuration - 用户无法理解
- apiPool 大小 - 用户无感知

## 八、总结

### 8.1 审查报告核心问题

1. **过度技术化**：35 项建议中约 60% 用户无感知，属工程自嗨
2. **缺量化数据**：0 项建议给出量化收益（启动时间、崩溃率、内存占用等）
3. **优先级失衡**：用户痛点（配置不生效、启动慢、网络卡顿）被定为 P1，而用户无感知的工程正确性（@Volatile）占 P0 配额
4. **低端机型保护缺失**：默认值未按设备分级，对低端机型 UX 不友好
5. **缺用户沟通方案**：未规划 updateLog.md 沟通内容，用户无法感知优化价值

### 8.2 核心建议

- **立即实施**：UX-P0 共 7 项（含 4 项从 P1 升级）
- **暂缓实施**：P0-6（Coroutine.async scope 改造），需先收集协程泄漏的实际用户投诉证据
- **合并简化**：35 项 → 22 项，减少 13 项冗余
- **新增配置**：性能模式三档开关，替代技术参数暴露
- **补量化数据**：实施前先采集基线（启动时间、崩溃率、内存峰值），实施后量化收益
