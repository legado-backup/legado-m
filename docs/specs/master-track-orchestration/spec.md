# spec.md — 三轨总线任务编排

## Intent

为三条任务轨（轨 A：compose-migration-status-audit；轨 B：legadoc-benchmark-analysis；轨 C：ng-benchmark-analysis）建立统一总线：裁决轨间执行顺序、识别待优化项先后、整合共性问题、治理跨轨冲突热点，产出可单线执行的波次计划。

## Scope

**纳入**：
1. 三轨全部分期的轨间排序与波次编排（不重复轨内函数级设计）
2. legadoc spec 悬置检查点（AD-03~06 裁决 + README 状态转正）的并入处置
3. 跨轨共性问题整合：DB 版本链、文件级串行热点（14 对单向）、公共前置、测试基建、UI 规范基线、缺口条款
4. 2 处文档缺口 + 1 处状态滞后补登
5. 外部活跃任务协调面（V 轨挂靠）：视频/下载/网络域 14 个活跃 spec 的协调闸门与占号登记；video-sniff-403-and-rss-classic-fix 由并行会话执行中，总线只做协调不接管实施

**排除**：
- 各分期实施级开发（另立实施 spec，引用原 spec 设计文档为权威）
- ui-style-unify-deep-fix 剩余实施（既有任务独立推进，仅作为公共闸门纳入编排）
- 各轨"不迁/暂缓"项的重新裁决（维持原 spec 决策）

## Approach

### Selected Approach

**静态依赖分析 + 波次时间窗编排**：以 3 子代理并行产出三轨结构化分析报告为事实源，主代理汇总出（a）待优化项优先级排序（按"真 bug > 安全加固 > 公共闸门 > 地基 > 旗舰 > 长尾 > 收官"分级），（b）共性整合矩阵，（c）W0-W5 波次计划（每波次内文件域零交集论证 + 窗口内推荐序）。检查点合并策略：legadoc 悬置裁决并入本总线检查点 1，一次审查解锁两 spec。

理由：三轨设计均已闭环/近闭环（轨 A 5 轮审核、轨 B 7 轮验证、轨 C 5 轮审查），无需重新设计，编排是纯调度问题；波次模型匹配实际单人+AI 协作的单线推进模式，"并行"表达为窗口内排序灵活性而非真并发。

### Alternatives Considered

| 替代方案 | 否决理由 |
|---------|---------|
| 三轨独立推进，不做总线编排 | 无法解决 DB 版本抢占（v109 已被 video-sniff 实占，P1/P3 需顺延）、ReadBookActivity 三方重写碰撞（C1+C2+reader-overlay）、真机测试窗口冲突；且 legadoc 悬置检查点无人解锁 |
| 按里程碑重新拆分混合批（跨轨混编任务组） | 打破各 spec 已定稿的轨内串行门禁（轨 A AD-07 禁跳批、轨 C P2 硬前置 P1），验收回执链断裂，风险大于收益 |
| 先集中完成轨 A 全部 B0-B5 再开 B/C 轨 | 轨 A B3+2/B4 是最重代码迁移段，期间 C0 真 bug（用户可感知内容错乱）与 P0 安全加固持续暴露风险，不满足"bug 优先"原则 |
| 用甘特图做资源级排期 | 单人+AI 协作无资源竞争维度，甘特粒度过细且维护成本高；波次+窗口内序已满足决策需要 |

### Drawbacks

| 已知缺点 | 接受理由 |
|---------|---------|
| 波次内多轨交替推进增加上下文切换成本 | 换取真 bug/安全项提前落地；每波次设窗口内推荐序降低切换频率 |
| 编排依赖三 spec 文档现状，轨内实施中若偏离设计需回写后再重排 | 各 spec 均有 AD 门禁（偏离先回写），总线只需响应式调整，成本低 |
| 检查点合并使本总线 spec 承担了 legadoc 的裁决职责 | 一次审查解锁两 spec，节省用户一轮完整检查点流程；裁决项在检查点中显式列出 |

### Prior Art

- 轨 C README 已示范"用户裁决 + 分期另立实施 spec"模式，本总线沿用该模式扩展到三轨
- 轨 B design.md 已建立"跨 spec DB 版本链登记机制"提议（db-version-registry.md），本总线将其落为 AD-02

## Requirements

- R1 波次计划必须给出每波次的：纳入分期、文件域隔离论证、窗口内推荐序、进入条件（前置闸门）
- R2 必须建立 DB 版本占号权威源（db-version-registry.md），所有含 DB 变更的分期实施前必须占号
- R3 文件级串行热点必须逐个列明冲突轨对与串行方向（谁先谁后）
- R4 legadoc 悬置检查点（AD-03~06）必须在本总线检查点 1 中显式列出供用户裁决
- R5 三轨间文档缺口（轨 C P3 缺 C1 正交声明、P5 缺 B3/B4 Rss 域时序条款）必须补登
- R6 每波次收束时必须回写本 spec 波次状态，保证总线与各 spec 状态一致
- R7 各分期开工前必须验证其进入条件真实满足（前置波次回执 + 文件域当前无他轨占用），禁止凭文档假设跳闸门
- R8 真机验证窗口为单设备共享资源：已显式排程窗口（W1 合并窗=B0 终测+light-theme S1-S9+video-sniff 待真机项；W4 独占窗=C2 排版回归，含 W3 末 D4 首次真机；其余分期真机项包含于其分期 L2/L3 收束验证），禁止多轨同时抢占同一窗口
- R9 V 轨挂靠只做协调（占号/串行闸门/真机窗口登记），不得改动 V 轨 spec 的任务归属与实施节奏；V 轨衔接为事件驱动建议单（收口事件→总线出建议单→并行会话确认→登记），确认前不排程
- R10 各分期实施 spec 的验证设计强度不得低于原 spec 分册声明（验证设计引用原分册为权威）；波次收束必须通过 L2 层验证（整包编译+全量单测+E2E 冒烟+热点 diff 审计）
- R11 提交执行一期一提交单元+提交前置五门禁（updateLog/文档同步/daemon 清场/日志残留=0/临时 Tag 清理），保证可按分期粒度回退

## Scenarios

- S1 正常推进：用户确认波次计划 → W0 闸门收口 → 逐波次推进，每波次收束回写状态 → 全轨完成
- S2 轨内延迟：某分期实施超窗（如 C2 27 人日跨窗）→ 该轨顺延占用下一窗口，同窗口其余轨不受阻，但文件域热点轨对必须重验串行方向
- S3 设计偏离：实施中发现与原 spec 设计不符 → 按该 spec AD 门禁先回写设计再改代码 → 总线波次表同步更新
- S4 用户改序：用户在任意波次收束点要求调整后续顺序 → 重排波次表并重验 R2/R3/R7/R8 约束 + 各轨轨内门禁（如轨 A 禁跳批）+ 涉及检查点重新确认 → 更新本 spec 后继续
- S5 V 轨进度偏离：并行会话实际进度快于/慢于编排假设（如提前完成 Phase3/4 或 enhance-switch）→ 以 v-track-registry 快照重算剩余串行序与衔接建议单 → 更新波次表后继续（不改 V 轨归属，R9）
