## 二、官方项目记忆机制深度分析（基于 https://docs.trae.cn/ide_memories）

### 2.1 官方机制核心特性

| 特性 | 实现方式 | 关键限制 |
|------|---------|---------|
| 记忆类型 | 全局记忆 + 项目记忆 | 仅两种类型，无对话级 |
| 存储路径 | C 盘 `~/.trae-cn/memory/` | 硬编码 C 盘，跨电脑不可共享 |
| 注入机制 | 系统自动注入 memory context | **仅识别官方位置**，项目目录不识别 |
| AI 管理 | 支持自动/按要求创建/修改/删除 | 依赖 AI 调用 Edit/Write 工具 |
| 手动管理 | 设置 > 规则与记忆 编辑文件 | 用户手动操作 |
| 持久化 | `session_memory_*.jsonl` 自动持久化 | 系统维护，AI 不直接读 |
| 不保存信息 | 临时指令/模糊偏好/敏感信息 | 由 AI 判断或用户指定 |

### 2.2 官方机制优点（5项）

| # | 优点 | 价值 | 不可替代性 |
|---|------|------|-----------|
| P1 | **系统自动注入 memory context** | 压缩恢复时 AI 无需主动读取即可获取记忆 | 🔴 高（项目目录无此能力） |
| P2 | **跨项目共享 user_profile.md** | 全局偏好跨项目统一 | 🔴 高（项目目录仅项目级） |
| P3 | **session_memory_*.jsonl 系统持久化** | 对话级自动备份，崩溃恢复 | 🟡 中（AI 不直接读但可作备份） |
| P4 | **标准化路径与原生支持** | TRAE IDE 原生识别，无适配成本 | 🟡 中（项目目录需 AI 主动读） |
| P5 | **手动管理入口** | 用户可在设置界面直接编辑 | 🟢 低（AI 也可编辑项目目录） |

### 2.3 官方机制缺点（7项，关键痛点）

| # | 缺点 | 影响 | 严重性 |
|---|------|------|--------|
| D1 | **C 盘路径硬编码** | Edit/Write 工具因工作区限制无法直接编辑，需依赖 PowerShell 间接写入 | 🔴 严重 |
| D2 | **多对话共享 project_memory.md** | 无对话级隔离，多窗口并发写入互相覆盖（铁证：用户反馈"防止多任务并发冲突"） | 🔴 严重 |
| D3 | **AI 无法获取 session_id** | 无状态感知，压缩恢复难以区分新旧对话 | 🔴 严重 |
| D4 | **project_memory.md 持续增长无归档** | 检索效率下降、上下文占用过大 | 🟡 中 |
| D5 | **时间戳获取工具问题** | mcp_Time 时区处理有误，12H 制导致时序错乱（铁证：真实 10:38 但记录 [12:00]） | 🔴 严重 |
| D6 | **无对话级独立记忆文件** | 任务级状态记录与恢复粒度粗 | 🟡 中 |
| D7 | **AI 与系统写入冲突** | AI 写入与系统自动注入可能不同步 | 🟡 中 |

### 2.4 改造点识别（基于优缺点分析）

| 改造点 | 对应缺点 | 改造方向 | 是否可独立完成 |
|--------|---------|---------|--------------|
| RP1 路径迁移 | D1 | 项目目录 `.trae/memory/projects/{key}/` | ✅ 可独立 |
| RP2 对话级隔离 | D2/D3/D6 | `conv_memory_{conv_id}.md` 独立文件 | ✅ 可独立 |
| RP3 归档机制 | D4 | 按时间(7天)/容量(50KB)/对话级三维度归档 | ✅ 可独立 |
| RP4 时间戳规范 | D5 | 禁 mcp_Time + 强制 PowerShell Get-Date 24H 制 | ✅ 可独立 |
| RP5 系统注入适配 | D7/P1 | 完全分离 or 双轨制 | ⚠️ 需权衡 |

## 五、整体规划：分层架构建议

### 5.1 三层架构（推荐）

```
┌─────────────────────────────────────────────────────────────┐
│ 第3层：系统层（TRAE IDE 维护，AI 不干预）                   │
│   - C 盘 ~/.trae-cn/memory/                                  │
│   - 系统自动注入 memory context                             │
│   - session_memory_*.jsonl 自动持久化                        │
│   - user_profile.md（全局共享）                              │
│   → AI 作为 P3 背景参考，不读不写                           │
├─────────────────────────────────────────────────────────────┤
│ 第2层：AI 主记忆层（AI 完全自主管理）                       │
│   - 项目目录 .trae/memory/projects/{key}/                   │
│   - ai_memory_main.md（Hard Constraints + 当前任务状态）    │
│   - {YYYYMMDD}/conv_memory_{conv_id}.md（对话级）           │
│   - archived/（归档目录）                                    │
│   → AI 作为 P1 权威源，主动读写                             │
├─────────────────────────────────────────────────────────────┤
│ 第1层：辅助层（补充经验索引）                                │
│   - basic-memory MCP（跨会话持久化）                         │
│   - 关键决策双写（AI 主记忆 + basic-memory）                │
│   → AI 作为 P2 辅助参考                                     │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 数据流分工

| 数据类型 | 系统层(C盘) | AI主记忆层(项目目录) | 辅助层(basic-memory) |

## 九、全局规范优化分析（用户2026-07-26 11:09反馈追加）

> 用户原文："全局规范现在哪些内容会影响你决策，或者是造成你困惑的，是不是也可以适度优化下呢？"
> 已审查全部 10 个全局规范文件（`~/.trae-cn/user_rules/`），识别出 6 个影响决策或造成困惑的核心问题。

### 9.1 影响决策或困惑的 6 个核心问题

#### 问题1：路径硬编码冲突（严重，影响压缩恢复决策）
- **涉及规范**：context-recovery.md + user_rules.md + budget-management.md
- **困惑点**：
  - context-recovery.md 第2件套要求读 `~/.trae-cn/memory/projects/{key}/project_memory.md`（C盘）
  - user_rules.md 第8行要求"记录到项目记忆中"（未明确路径）
  - budget-management.md 要求"缓存到memory"（未明确路径）
  - **与 AD-11 冲突**：AD-11 要求 AI 不读不写 C 盘官方位置
- **AI 决策困惑**：压缩恢复时读 C 盘还是项目目录？写入反馈时写哪里？
- **优化方向**：
  - context-recovery.md 第2件套改为"项目目录 ai_memory_main.md"
  - user_rules.md 明确"项目目录 .trae/memory/"
  - budget-management.md 明确"项目目录 .trae/memory/"

#### 问题2：对话 ID 机制缺失（严重，影响并发隔离决策）
- **涉及规范**：core-spec.md
- **困惑点**：
  - core-spec.md 未提及 conv_id 机制
  - 但 AD-14/AD-15 依赖 conv_id 实现任务级隔离和防错乱
  - AI 无法从 core-spec.md 获取对话 ID 规范指引
- **AI 决策困惑**：多对话并发时如何隔离？压缩恢复时如何识别当前对话？
- **优化方向**：core-spec.md 追加"对话级 conv_id 隔离"条款（指向 design.md AD-02/AD-14/AD-15）

#### 问题3：时间戳工具未规范（严重，影响时序准确性）
- **涉及规范**：user_rules.md
- **困惑点**：
  - user_rules.md 第8行要求"24H制"，但未禁 mcp_Time
  - 未强制 PowerShell Get-Date
  - 铁证：mcp_Time 时区处理问题导致 [2026-07-26 12:00] 错乱
- **AI 决策困惑**：应该用哪个工具获取时间戳？
- **优化方向**：user_rules.md 明确"禁 mcp_Time + 强制 PowerShell Get-Date -Format 'yyyy-MM-dd HH:mm:ss'"

#### 问题4：对话级文件隔离未覆盖（中等，影响并发安全决策）
- **涉及规范**：concurrent-editing.md
- **困惑点**：
  - concurrent-editing.md 只覆盖"源码修改串行化"
  - 未覆盖"对话级记忆文件隔离"
  - AI 不确定记忆文件是否需要像源码一样串行化
- **AI 决策困惑**：多对话并发时，记忆文件是否需要串行化？
- **优化方向**：concurrent-editing.md 追加"对话级文件隔离"条款（每个对话只 Edit 自己的 conv_memory）

#### 问题5：缓存路径不明（中等，影响工具调用决策）
- **涉及规范**：budget-management.md
- **困惑点**：
  - "避免重复读取同一文件缓存到memory"——未明确 memory 是哪个
  - AI 可能误把缓存写到 C 盘（违反 AD-11）或写到错误位置
- **AI 决策困惑**：缓存应该写到哪里？
- **优化方向**：budget-management.md 明确"缓存到项目目录 .trae/memory/cache/"

#### 问题6：危险操作边界模糊（低，影响创建目录决策）
- **涉及规范**：danger-ops.md
- **困惑点**：
  - "禁止删除目录: ~/.trae-cn/"——但创建项目目录 .trae/memory/ 是否算危险操作？
  - AI 可能误判创建 .trae/memory/ 为危险操作而请求确认
- **AI 决策困惑**：创建项目目录 .trae/memory/ 是否需要 AskUserQuestion 确认？
- **优化方向**：danger-ops.md 明确"项目目录 .trae/memory/ 创建不算危险操作（在工作区内）"

### 10.1 三大工具核心机制速览

| 工具 | 核心机制 | 最成熟点 |
|------|---------|---------|
| **Claude Code** | 5层架构+4类分类+Auto Dream+4级压缩 | "记忆只是提示"原则+只记无法派生认知 |
| **Cursor** | Rules+Memories双轨制+.mdc格式 | 4种触发类型（Always/Auto/Manual/Agent request） |
| **Cline** | Memory Bank三层架构+6类核心文件 | new_task工具+版本控制集成 |

### 10.2 我们设计的8项差距

| # | 差距 | 影响 | 借鉴来源 |
|---|------|------|---------|
| G1 | 缺"记忆只是提示"原则 | 凭记忆产生幻觉 | Claude Code |
| G2 | 缺"只记无法派生认知"原则 | 记忆冗余+过期 | Claude Code |
| G3 | 记忆分类不够语义化 | 检索效率低 | Claude Code 4类 |
| G4 | 缺索引文件行数限制 | 主记忆无限增长 | Claude Code 200行 |
| G5 | 缺Auto Dream自动整理 | 冲突记忆累积 | Claude Code |
| G6 | 缺条件触发机制 | 所有规范始终应用 | Cursor 4种触发 |
| G7 | 缺相对日期转绝对日期 | 时间锚点丢失 | Claude Code |
| G8 | 缺版本控制集成 | 记忆不可追溯 | Cline/Claude Code |

### 10.3 建议新增 5 个 ADR（AD-16 至 AD-20）

| ADR | 标题 | 借鉴来源 | 优先级 |
|-----|------|---------|--------|
| AD-16 | "记忆只是提示"原则 | Claude Code | P0 |
| AD-17 | "只记无法派生认知"原则 | Claude Code | P0 |
| AD-18 | 4类记忆分类 | Claude Code | P0 |
| AD-19 | 索引文件200行限制 | Claude Code | P1 |
| AD-20 | 版本控制集成 | Cline/Claude Code | P1 |

### 10.4 建议修订 3 个既有 ADR

| ADR | 追加条款 | 借鉴来源 |
|-----|---------|---------|
| AD-07 时间戳规范 | 相对日期必须转绝对日期 | Claude Code |
| AD-08 归档机制 | 定期整理机制（Auto Dream） | Claude Code |
| AD-14 任务级记忆 | 压缩前状态传递（new_task） | Cline |

### 10.5 不建议借鉴的设计（4项）

1. ❌ Claude Code 的投机执行（Copy-on-Write 过于复杂）
2. ❌ Claude Code 的 20 项 Shell 安全检查（本项目非 Shell 密集型）
3. ❌ Cursor 的 BugBot（与记忆机制无关）
4. ❌ Cline 的语义嵌入算法（实现成本过高）

### 10.6 研究结论

1. **Claude Code 最成熟**：5层架构+4类分类+Auto Dream+4级压缩，设计最完整
2. **Cursor 最简洁**：Rules+Memories 双轨制，.mdc 格式清晰
3. **Cline 最结构化**：6类核心文件+三层架构，适合团队协作
4. **我们的设计有独特优势**：对话级 conv_memory 文件隔离多任务并发
5. **但存在8项差距**：需借鉴行业最佳实践补齐
