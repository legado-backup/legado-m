## 三、过度约束/干扰AI工作的条款（重点）

⚠️ 本节是用户最关心的维度，深入分析每个条款对AI工作流程的影响。

### 3.1 【P0-严重干扰】"所有交互强制必须使用AskUserQuestion工具"

**来源**：user_rules.md 第8行
**原文**："所有交互强制必须使用AskUserQuestion工具询问用户"

**干扰方式**：
- AI在完成简单的查询类任务（如"这个文件在哪里"、"这个函数做什么"）后，仍然必须调用AskUserQuestion询问用户是否满意。
- 这种强制交互打断了用户的工作流——用户问一个简单问题，还得回答"是否满意？"，增加无意义的往返。
- 对于信息提供类任务（如分析报告、技术说明），强制AskUserQuestion让回复格式变得僵硬。

**干扰场景示例**：
1. 用户问"concurrent-editing.md在哪里？" → AI回答路径后，还得AskUserQuestion问"是否满意？"
2. 用户问"分析这段代码" → AI给出分析后，还得AskUserQuestion问"是否需要调整？"
3. 用户问"查找所有包含XXX的文件" → AI给出列表后，还得AskUserQuestion问"是否满意？"

**优化建议**：
区分交互类型，仅以下场景强制AskUserQuestion：
- 需要用户决策的多方案选择
- 危险操作前的确认
- 任务交付验收（代码变更类任务）
- OpenSpec检查点

信息提供类任务（查询、分析、说明）不强制AskUserQuestion，AI可以正常文字回复结束。

### 3.2 【P0-严重干扰】"回复的最后一个工具调用必须是AskUserQuestion"

**来源**：core-spec.md 第8行
**原文**："铁律: 回复的最后一个工具调用必须是AskUserQuestion,禁止用文字总结/建议/汇报代替交互确认"

**干扰方式**：
- 强制最后一个工具调用必须是AskUserQuestion，意味着AI不能以正常文字回复结束。
- 对于纯分析、纯查询任务，AI已经给出完整答案，还必须调用AskUserQuestion，导致输出格式僵硬。
- 与budget-management.md的"单次回复正文≤100行"冲突——AskUserQuestion本身也占输出空间。
- 在子代理任务中，子代理的最后一个工具调用也必须是AskUserQuestion吗？规范未明确，导致子代理困惑。

**干扰场景示例**：
1. AI完成代码分析，输出100行分析报告 → 还得调用AskUserQuestion问"是否满意？" → 用户看到分析报告后，还得点击"通过"
2. 子代理完成文档生成 → 是否需要AskUserQuestion？规范未明确

**优化建议**：
1. 区分任务类型：
   - 代码变更类任务：必须以AskUserQuestion结束（需要验收）
   - 信息提供类任务：可以文字回复结束
   - 子代理任务：子代理不强制AskUserQuestion，由主代理统一询问
2. 改为"任务交付前必须AskUserQuestion验收，而非每次回复都必须AskUserQuestion"。

### 3.3 【P0-严重干扰】"禁止自以为是认为任务结束主动终止对话"

**来源**：user_rules.md 第8行 + core-spec.md 第3行
**原文**："禁止自以为是认为任务结束主动终止对话！！！"

**干扰方式**：
- "自以为是"是主观判断，AI难以执行——AI如何判断自己是否"自以为是"？
- 实际效果是：AI不敢正常结束回复，每次都得AskUserQuestion，即使任务明显已完成。
- 与"展示结果≠用户确认"叠加，导致AI在给出任何结果后都必须AskUserQuestion。

**干扰场景示例**：
1. 用户问"今天几号？" → AI回答"2026-07-27" → 是否需要AskUserQuestion？根据规范，似乎需要。
2. 用户说"读取这个文件" → AI读取并展示内容 → 是否需要AskUserQuestion？根据规范，似乎需要。

**优化建议**：
1. 删除"自以为是"的主观表述。
2. 改为客观规则："以下场景必须AskUserQuestion：代码变更交付、危险操作确认、多方案选择、OpenSpec检查点。其他场景可正常结束回复。"

### 3.4 【P1-中度干扰】"输出双重验证清单(强制)"

**来源**：context-recovery.md 第26-29行
**原文**："输出双重验证清单(强制): 1.已加载项目主规范 2.已加载用户反馈清单 3.已确认当前任务状态"

**干扰方式**：
- 压缩恢复后必须输出三重验证清单（虽然叫"双重"但列了3项，本身就是矛盾）。
- 每次压缩恢复都要输出清单，占用宝贵的上下文和输出空间。
- 用户并不需要看到这些清单——这是AI的内部验证，不应强制输出给用户。

**干扰场景**：
压缩恢复后，AI本应直接恢复工作，但必须先输出三重验证清单，增加延迟。

**优化建议**：
1. 验证清单改为内部检查（AI在思考中完成），不强制输出到用户。
2. 仅在验证失败时输出报告。
3. 修复"双重"vs"三重"的命名矛盾。

### 3.5 【P1-中度干扰】"单次回复正文≤100行"

**来源**：budget-management.md 第10行
**原文**："单次回复正文≤100行超出用Write写文件"

**干扰方式**：
- 硬性限制100行，对于复杂的技术分析、代码解释等内容，100行可能不够。
- AI需要在内容完整性和行数限制之间权衡，可能导致内容被截断或拆分到多个文件。
- 与"AskUserQuestion强制"叠加：AskUserQuestion本身也占行数，进一步压缩可用输出空间。
- 100行的硬性限制缺乏弹性——复杂任务的分析报告可能需要150-200行。

**干扰场景**：
1. 代码审查报告 → 100行不够 → 必须Write到文件 → 用户得打开文件看
2. 多文件分析 → 100行不够 → 必须拆分到多个回复

**优化建议**：
1. 改为"建议≤100行，超出时优先用Write写文件"，而非硬性限制。
2. 增加例外：代码审查、技术分析等场景可放宽到200行。
3. AskUserQuestion的行数不计入100行限制。

### 3.6 【P1-中度干扰】"强制四件套并行 / 缺失时暂停报告"

**来源**：context-recovery.md 第9行
**原文**："强制要求: ...四件套并行 / 缺失时暂停报告"

**干扰方式**：
- 强制四件套并行读取，缺失任何一件就暂停报告。
- 但如果某个文件本身不存在（如项目记忆文件未创建），AI会卡住，无法继续工作。
- "暂停报告"过于绝对——即使是次要文件缺失，也会阻塞整个工作流。

**干扰场景**：
1. 新项目首次使用 → ai_memory_main.md不存在 → AI暂停报告，无法工作
2. TaskList工具临时不可用 → AI暂停报告，无法工作

**优化建议**：
1. 区分"文件不存在"和"文件存在但未读取"：
   - 文件不存在：自动创建（如ai_memory_main.md）或继续工作（如非关键文件）
   - 文件存在但未读取：补读
2. 仅当关键文件（AGENTS.md、core-spec.md）缺失时才暂停报告。
3. 修复"四件套"为"五件套"。

### 3.7 【P1-中度干扰】"触发条件自查(对话开始时)"检查8项

**来源**：core-spec.md 第10-18行
**原文**：列出8个触发条件，要求"对话开始时"自查

**干扰方式**：
- 对话开始时要检查8个触发条件，每个条件可能需要Read一个文件。
- 这增加了对话开始的开销，特别是对于简单任务（如"读取这个文件"）。
- "对话开始时"检查所有条件，但实际上很多条件在简单任务中不会触发。

**干扰场景**：
1. 用户说"读取X文件" → AI开始检查8个触发条件 → 实际上只需要Read文件
2. 用户说"今天几号" → AI开始检查8个触发条件 → 完全不必要

**优化建议**：
1. 改为"按需加载"而非"对话开始时全部检查"。
2. 仅在用户消息明确触发某条件时才加载对应规范。
3. 增加"简单任务快速通道"：单文件读取、简单查询等不触发规范加载。

### 3.8 【P1-中度干扰】"低风险强制子代理"

**来源**：budget-management.md 第5行
**原文**："低风险(文档生成/代码分析/大文件读取): 强制子代理"

**干扰方式**：
- 强制子代理意味着即使是简单的文档生成也必须用子代理，增加了编排开销。
- 对于短文档（如简单的README），用子代理反而更慢。
- "大文件"未定义具体阈值，AI难以判断。

**干扰场景**：
1. 生成50行README → 强制子代理 → 编排开销 > 实际生成时间
2. 读取20KB文件 → 是否算"大文件"？规范未明确

**优化建议**：
1. 增加例外："文档<500行或文件<50KB时不强制子代理"。
2. 明确"大文件"定义（如">100KB"）。
3. 改为"推荐子代理"而非"强制子代理"。

### 3.9 【P1-中度干扰】"用户反馈按时间倒序插入到正确位置"

**来源**：context-recovery.md 第37行
**原文**："追加位置: 按时间倒序插入到正确位置(最新在最前),禁止直接追加到末尾"

**干扰方式**：
- 要求AI在追加用户反馈时按时间排序插入，这增加了Edit的复杂度。
- AI需要先Read整个反馈列表，找到正确位置，再精确Edit。
- 对于频繁的反馈记录，这非常低效——每次记录反馈都要Read+Edit两次操作。

**干扰场景**：
1. 用户连续3次反馈 → AI每次都要Read整个反馈列表，找位置，精确Edit → 6次工具调用
2. 反馈列表很长 → 找正确位置的Edit难度增加，容易出错

**优化建议**：
1. 改为"最新反馈放在文件开头的'最近反馈'区块，旧反馈按时间倒序排列"。
2. 或允许追加到末尾，定期整理排序。
3. 或采用"每日反馈独立区块"结构，避免插入排序。

### 3.10 【P2-轻度干扰】"工具调用≥30次时主动/compact或用子代理分担"

**来源**：budget-management.md 第13行
**原文**："单次对话工具调用≥30次时主动/compact或用子代理分担"

**干扰方式**：
- 30次工具调用是一个较低的阈值，对于复杂任务很容易超过。
- AI需要频繁关注工具调用次数，分散注意力。
- "主动/compact"可能打断工作流——AI正在执行任务时突然compact，会丢失上下文。

**优化建议**：
1. 提高阈值到50次。
2. 或改为"当上下文使用超过70%时"才触发。
3. 增加"任务阶段完成时才compact"的例外。

### 3.11 【P2-轻度干扰】"Edit前备份上下文: 对核心文件Edit前先Read确认当前内容"

**来源**：concurrent-editing.md 第10行
**原文**："Edit前备份上下文: 对核心文件Edit前先Read确认当前内容"

**干扰方式**：
- 每次Edit前都要Read，增加了工具调用。
- 虽然这是为了防止并发修改，但对于单Agent场景是冗余的。
- 与budget-management.md的"避免重复读取同一文件"冲突。

**优化建议**：
1. 仅在多Agent并行时强制Read，单Agent场景可以跳过。
2. 或改为"对核心文件Edit前，若距上次Read超过5次工具调用，则重新Read"。

### 3.12 【P2-轻度干扰】"禁止以'避免触发思考上限'为由建议用户新开对话"

**来源**：budget-management.md 第2行
**原文**："禁止以'避免触发思考上限'为由建议用户新开对话"

**干扰方式**：
- 当上下文真的接近满且compact无效时，AI不能建议新开对话，只能自己想办法。
- 但如果子代理也无法分担，AI会陷入困境——无法完成任务，也无法建议用户。
- 规范假设"子代理+compact"总能解决问题，但实际上可能不行。

**优化建议**：
1. 保留禁止"以避免触发上限为由"建议。
2. 增加例外："当子代理和compact都无效时，可向用户说明情况并建议新开对话"。

## 四、缺失的关键条款分析

### 4.1 缺失：子代理错误传播机制

**问题**：当前规范规定了何时使用子代理，但未规定子代理失败时的处理。子代理可能返回错误结果、超时、或返回不完整内容，主代理需要验证子代理的输出。

**补充建议**：增加"子代理输出验证"条款：
- 子代理返回后，主代理必须验证关键输出（如文件是否实际创建、代码是否实际修改）
- 子代理失败时，主代理应重试或降级为直接执行
- 子代理超时（>5分钟）时，主代理应终止并接管任务

### 4.2 缺失：规范版本管理

**问题**：6个规范文件没有版本号、更新时间、变更记录。无法追踪规范的演进，也无法判断AI是否在使用最新版本。

**补充建议**：每个规范文件增加头部元信息：
```markdown
> 版本：1.0
> 更新时间：2026-07-27
> 变更摘要：XXX
```

### 4.3 缺失：规范冲突解决优先级

**问题**：当多个规范文件之间冲突时，没有明确的优先级。虽然core-spec.md自称"最高优先级"，但其他文件也有"强制"标签（如danger-ops.md的"违反将导致不可逆的数据丢失"）。

**补充建议**：明确优先级链：
```
danger-ops.md (安全底线，最高)
> output-safety.md (输出安全)
> core-spec.md (核心规范)
> context-recovery.md (压缩恢复)
> budget-management.md (预算管理)
> concurrent-editing.md (并发控制)
> user_rules.md (用户基础规则)
```

### 4.4 缺失：AI工作流中断恢复机制

**问题**：规范了压缩恢复，但未规范其他中断场景的恢复：
- 工具调用失败（如RunCommand超时）
- 子代理失败
- 网络异常
- 用户手动中断

**补充建议**：增加"中断恢复通用机制"条款：
- 中断后重新执行时，先读取项目记忆的"当前任务状态"
- 跳过已完成的步骤
- 从中断点继续，而非重新开始

### 4.5 缺失：规范自身的优化反馈机制

**问题**：规范要求AI记录用户反馈，但未要求AI记录"规范本身导致的问题"。AI无法反馈"某条规范让我困惑"或"某条规范相互矛盾"。

**补充建议**：增加"规范问题反馈"条款：
- AI遇到规范自身问题时，在项目记忆的"规范问题"区块记录
- 格式：[日期] 规范文件 | 行号 | 问题描述 | 建议优化
- 定期由用户审阅并优化规范

### 4.6 缺失：任务复杂度评估机制

**问题**：规范用"50+文件"、"30次工具调用"等量化阈值，但缺少对任务复杂度的综合评估。简单任务和复杂任务适用同样的约束，导致简单任务过度约束。

**补充建议**：增加"任务复杂度评估矩阵"：
| 复杂度 | 文件数 | 工具调用 | 适用约束 |
|--------|--------|---------|---------|
| 简单 | ≤3 | ≤10 | 轻约束（不强制子代理、不强制AskUserQuestion） |
| 中等 | 4-15 | 11-30 | 中约束（推荐子代理、关键节点AskUserQuestion） |
| 复杂 | 16-50 | 31-60 | 重约束（强制子代理、阶段验收AskUserQuestion） |
| 超复杂 | >50 | >60 | 五阶段流水线（强制子代理、每阶段AskUserQuestion） |

### 4.7 缺失：单Agent vs 多Agent场景区分

**问题**：多数规范假设多Agent并行场景（如concurrent-editing.md），但单Agent场景下很多约束是冗余的。

**补充建议**：明确区分单Agent和多Agent场景：
- 单Agent场景：concurrent-editing.md的大部分约束不适用
- 多Agent场景：concurrent-editing.md全部约束适用
- AI根据是否使用子代理判断当前场景

### 4.8 缺失：上下文使用率监控机制

**问题**：规范了工具调用次数，但未规范上下文使用率的监控。AI可能工具调用少但上下文已满（如读取大文件）。

**补充建议**：增加"上下文使用率监控"条款：
- 上下文使用率≥70%时预警，优先用子代理分担
- ≥85%时强制compact或子代理
- ≥95%时向用户说明情况

## 七、总结

### 7.1 核心发现

1. **过度约束是最大问题**：
   - AskUserQuestion的强制使用范围过广，干扰了简单查询、分析类任务的正常完成。
   - "所有交互强制AskUserQuestion"+"最后一个工具调用必须是AskUserQuestion"+"禁止自以为是"三条叠加，导致AI在每次回复后都必须AskUserQuestion，即使任务明显已完成。
   - 这是用户最关心的"干扰AI工作的主规范条款"，建议优先修复。

2. **内部矛盾严重**：
   - context-recovery.md存在五件套vs四件套、任务状态权威源的内部矛盾。
   - "输出双重验证清单"标题说双重，实际3项。
   - 这些矛盾让AI困惑，不知道该执行哪个规则。

3. **冗余严重**：
   - AskUserQuestion规范在3处重复，项目记忆路径在4处重复，时间戳规则在3处重复。
   - 冗余增加上下文负担，也增加维护成本（改一处得改多处）。

4. **场景缺失**：
   - 未区分单Agent vs 多Agent、简单任务 vs 复杂任务。
   - 所有任务适用同样的约束，导致简单任务过度约束。

5. **主观表述多**：
   - "自以为是"、"大文件"、"系统注入滞后"等表述模糊，AI难以执行。

### 7.2 优化方向

1. **分层约束**（核心方向）：
   - 根据任务复杂度分层（简单/中等/复杂/超复杂），不同层级适用不同约束。
   - 简单任务轻约束（不强制子代理、不强制AskUserQuestion），复杂任务重约束。
   - 这能解决大部分"过度约束"问题。

2. **场景区分**：
   - 明确区分单Agent和多Agent场景。
   - 单Agent场景下，concurrent-editing.md的大部分约束不适用。

3. **去重合并**：
   - 合并重复条款，统一到core-spec.md。
   - 其他文件仅引用core-spec.md，不重复内容。

4. **修复矛盾**：
   - 优先修复context-recovery.md的内部矛盾（五件套vs四件套、任务状态权威源）。
   - 修复"双重"vs"三重"的命名矛盾。

5. **补充缺失**：
   - 增加规范版本管理、冲突解决优先级、中断恢复机制、子代理错误传播机制。
   - 增加任务复杂度评估矩阵。

6. **客观化表述**：
   - 将"自以为是"等主观表述改为客观规则。
   - 明确"大文件"、"验收"等术语的定义。

### 7.3 预期效果

通过以上优化：
- **AI工作效率提升**：简单任务不再被过度约束，减少无意义的AskUserQuestion往返。
- **AI困惑减少**：修复内部矛盾，统一术语，AI执行更确定。
- **上下文负担降低**：去重合并后，规范文件更精简，占用上下文更少。
- **可维护性提升**：规范版本管理+冲突解决优先级，便于后续演进。
