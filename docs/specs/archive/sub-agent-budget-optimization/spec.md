# Spec：子代理编排与思考预算优化

## Intent

解决 GLM-5.2 在 Trae 平台频繁触发"模型思考次数已达上限"的问题，**在不增加成本（不开新对话）的前提下，最大化同对话内的工作量**，提升 AI 执行复杂任务（如 OpenSpec 流程）的连续性和效率。

## Scope

### 包含

- 强制子代理的触发条件与执行规范
- 主代理对子代理的监控机制（同步/异步/查询/补充）
- 子代理产出的质量保证体系（prompt 规范+二次验证+失败重试）
- 与现有规范体系（AGENTS.md "复杂任务处理流程"、"并发文件修改规范"、OpenSpec 工作流程）的协调与修改
- 新增子规范 `sub-agent-quality-management.md`
- 禁止以"避免思考上限"为由建议新对话的规则

### 不包含

- 不修改 GLM-5.2 模型本身或 Trae 平台配置
- 不涉及 Trae 平台"工具调用轮次"等设置项的调整（用户侧操作）
- 不改变现有计费模式
- 不涉及代码层面（Kotlin/Java）的变更

## Approach

### Selected Approach：强制子代理编排（同对话内虚拟拆分）

**核心思路**：子代理有独立的工具调用预算、思考 token 预算、上下文窗口，但不额外开新对话、不额外收费。利用这一特性，将大任务委托给子代理执行，主对话只负责调度和验证，从而在同对话内扩展工作量。

**选定理由**：
1. 子代理是**唯一能同时解决工具调用轮次+思考 token+上下文累积**的手段
2. 子代理**不额外收费**（同对话内），符合"省钱"诉求
3. 子代理有独立预算，**真正降低触发思考上限的概率**
4. Trae 平台原生支持 Agent 工具，无需额外基础设施

### Alternatives Considered

| 替代方案 | 描述 | 否决理由 |
|---------|------|---------|
| **任务拆分到多次对话** | OpenSpec 每个阶段独立对话，单次对话工具调用≥30次主动建议新对话 | ❌ 新对话收费，一次新对话一次钱，直接增加成本，背离"省钱"诉求 |
| **长输出写文件** | 长内容用 Write 写文件，正文只给摘要 | ⚠️ 只对"上下文累积"有效，对"工具调用轮次"和"思考 token"无效，效果有限 |
| **OpenSpec 分文档生成** | 四文档分多次 Write 调用 | ⚠️ 同对话内工具调用次数相同（4次），不减少触发概率；只有分多次对话才有效，但分对话收费 |
| **分阶段 /compact** | 检查点间主动 /compact 压缩上下文 | ⚠️ 只对"上下文累积"有效，对"工具调用轮次"可能无效（若轮次累积计数不重置） |
| **调整 Trae 工具调用轮次设置** | 用户在 Trae 设置中调高默认值（200→更高） | ❌ 用户侧操作，非规范层；且调高会降低回答质量（官方建议≤50） |
| **关闭 GLM-5.2 思考模式** | 从 Max 降到 High | ❌ 复杂任务质量下降；且 Trae 不一定支持用户自定义 |

### Drawbacks

| 缺点 | 接受理由 |
|------|---------|
| 子代理调用有额外开销（启动子代理+prompt 传递） | 远小于触发思考上限后"继续"或新对话的成本 |
| 主代理需要学习监控和验证子代理产出 | AGENTS.md 已有"子代理产出验证"规则，本次只是强化 |
| 子代理可能产出不合格，需要重试 | 通过质量保证体系（明确 prompt+二次验证+失败重试）控制 |
| 子代理与"并发文件修改规范"有潜在冲突（源码文件串行化） | 通过职责分离解决：子代理只做分析/文档，源码修改由主代理串行执行 |
| 子代理本身也可能触发思考上限 | 子代理任务粒度更小（≤12文件），触发概率低；且子代理触发不影响主对话 |
| 子代理的思考过程不透明，主代理难以知道子代理"怎么想的" | 子代理返回最终结果即可，主代理基于结果验证，不需要知道思考过程 |

### Prior Art

- AGENTS.md 现有"复杂任务处理流程"已使用子代理（≤12文件/子代理），但触发阈值过高（50+文件）
- core-spec 已强调"批量并行工具调用"
- OpenSpec 步骤5已有"子代理产出验证"规则（红色标记）

## Requirements

### R1：分级子代理策略（低风险强制，高风险禁止）

**低风险任务（✅ 强制子代理）**：
- **R1.1** 文档生成任务（OpenSpec 四文档/分析报告）必须用子代理执行
- **R1.2** 代码分析任务（源码探索/架构分析/Grep+Read 搜索）必须用子代理执行
- **R1.3** 单文件 > 500 行的读取分析必须用子代理执行
- **R1.4** OpenSpec 步骤2（生成四文档）必须用子代理并行生成

**中风险任务（🟡 推荐子代理）**：
- **R1.5** OpenSpec 步骤5（实施）的分析阶段推荐用子代理，源码修改由主代理串行执行
- **R1.6** 涉及 ≥ 5 个源文件的探索任务推荐用子代理
- **R1.7** 预计 ≥ 10 次工具调用的分析任务推荐用子代理

**高风险任务（❌ 禁止子代理，主代理直接执行）**：
- **R1.8** 架构决策/方案选择必须由主代理直接执行（需要用户偏好和上下文）
- **R1.9** 源码文件修改（Edit）必须由主代理串行执行（遵守并发文件修改规范）
- **R1.10** 用户交互（AskUserQuestion）必须由主代理直接执行
- **R1.11** 深度分析任务（源码深挖/多方案对比）若需要用户反馈上下文，由主代理直接执行

### R2：主代理监控机制

- **R2.1** 默认使用同步模式（`run_in_background: false`），主代理等待子代理完成
- **R2.2** 主代理可用 TaskOutput 工具查询子代理输出，`block=true` 等待完成
- **R2.3** 主代理可用 SendMessage 工具向子代理发送补充指令
- **R2.4** 异步模式（`run_in_background: true`）仅用于独立的后台任务（如文档同步）

### R3：子代理质量保证

- **R3.1** 子代理 prompt 必须包含：任务描述+输入清单+期望输出格式+验证标准
- **R3.2** 主代理收到子代理结果后必须二次验证：
  - 新增文件 → Read 确认文件存在 + 关键代码段存在
  - 修改文件 → Grep 确认变更内容确实存在
  - 代码编译 → 运行编译确认无错误
  - 功能实现 → Grep+Read 确认函数签名存在 + 逻辑非空壳
- **R3.3** 验证不合格时，主代理 SendMessage 修正或重新启动子代理
- **R3.4** 子代理产出必须包含"完成级别"声明（Level 1/2/3）

### R4：规范冲突处理

- **R4.1** 与"并发文件修改规范"的冲突：子代理只做分析/文档任务，**禁止修改源码文件**；源码修改由主代理串行执行
- **R4.2** 与"复杂任务处理流程"的协调：降低触发阈值（50+文件→5+文件或10+工具调用），保留≤12文件/子代理上限
- **R4.3** 与 OpenSpec 工作流程的修改：步骤2和步骤5引入子代理
- **R4.4** 与 core-spec 交互规范的协调：子代理不直接与用户交互，主代理负责所有 AskUserQuestion

### R5：禁止建议新对话

- **R5.1** 禁止以"避免触发思考上限"为由建议用户新开对话
- **R5.2** 触发上限时，优先输入"继续"续接
- **R5.3** "继续"后仍频繁触发时，用子代理分担后续工作
- **R5.4** 仅当上下文窗口接近满（>90%）且 /compact 无效时，才向用户说明情况并提供建议

### R6：减少主对话消耗

- **R6.1** 长输出（>100 行）必须用 Write 写文件，正文只给摘要
- **R6.2** 工具调用结果不回显，直接基于结果给结论
- **R6.3** 批量并行工具调用优先（一次调用多个独立工具）
- **R6.4** 避免重复读取同一文件，已读内容缓存到 memory

### R7：质量保证强化（针对上下文割裂风险）

- **R7.1** 子代理 prompt 必须包含关键约束：用户偏好（lazy principle/AskUserQuestion/输出安全）+ 项目规范引用（AGENTS.md 路径）+ 验证标准
- **R7.2** 主代理二次验证强化：不只是 Read 确认存在，还要逻辑检查；重要产出对照用户反馈验证
- **R7.3** 子代理 prompt 必须传递当前任务的用户反馈摘要（若有）
- **R7.4** 子代理产出必须包含"完成级别"声明（Level 1/2/3）+ "潜在问题"说明

### R8：实验性标注与兜底机制

- **R8.1** 本规范标注为"实验性规范 V1"，首次使用时观察效果
- **R8.2** 保留兜底机制：触发上限时优先"继续"续接
- **R8.3** "继续"后仍频繁触发时，才用子代理分担后续工作
- **R8.4** 如果发现子代理也触发主对话上限（说明预算不独立），调整为"减少输出+/compact"策略
- **R8.5** 如果发现子代理降低质量，收紧高风险任务范围（更多任务由主代理直接执行）

## Scenarios

### 场景1：OpenSpec 生成四文档（高触发风险）

**当前行为**：主代理一次性输出 README+spec+design+tasks，正文输出文档内容，必然触发思考上限。

**优化后行为**：
1. 主代理启动 1 个子代理，prompt 包含四文档的完整需求
2. 子代理并行生成四文档（用 Write 写文件）
3. 主代理收到子代理完成通知
4. 主代理 Read 确认四个文件存在
5. 主代理正文只汇报"已生成四文档，核心决策是 xxx"
6. 主代理调用 AskUserQuestion 进入检查点1

**预期效果**：主对话工具调用 ≤ 5 次（启动子代理+Read×4+AskUserQuestion），不触发思考上限。

### 场景2：OpenSpec 实施涉及多文件修改

**当前行为**：主代理按 tasks.md 顺序连续 Edit 多个文件，工具调用累积触发上限。

**优化后行为**：
1. 主代理启动子代理执行分析阶段（Grep+Read 探索相关代码）
2. 主代理收到子代理分析结果
3. 主代理基于分析结果，串行执行源码 Edit（遵守并发文件修改规范）
4. 每完成 3 个任务，主代理主动 /compact

**预期效果**：主对话工具调用减少 60%+，不触发思考上限。

### 场景3：深度分析任务（如日志分析）

**当前行为**：主代理读取大量日志，输出长分析，触发思考上限。

**优化后行为**：
1. 主代理启动子代理，prompt 包含日志文件路径+分析要求
2. 子代理读取日志，在子代理上下文内深度分析
3. 子代理返回结构化分析报告（异常类型/错误码/调用栈/结论）
4. 主代理基于报告给用户汇报

**预期效果**：主对话不读取大日志文件，思考 token 不消耗在主对话，不触发上限。

### 场景4：触发思考上限后的恢复

**当前行为**：触发上限 → 输入"继续" → 很快又触发 → 最终新对话。

**优化后行为**：
1. 触发上限 → 输入"继续"续接
2. 主代理识别到已触发上限，后续工作改为子代理执行
3. 主代理只做调度和验证，不再直接执行大任务
4. 避免"继续"后再次触发

**预期效果**："继续"后不再频繁触发，避免新对话。
