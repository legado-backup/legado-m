> 审查日期：2026-07-25

## 一、产品用户体验角度

### P0 严重问题（必须修复）

**[UX-P0-1] UI 兼容字段未处理导致用户困惑**
- **问题**：`pref_config_other.xml` 中三个配置项（搜索线程数 / 更新和缓存线程数 / 通用线程数兼容字段）同时显示且都可点击修改，新用户看到"通用线程数（兼容字段）"会困惑该改哪一项
- **影响**：用户可能在兼容字段上修改导致配置不一致（兼容字段值与实际生效的 searchThreadCount/updateCacheThreadCount 不一致）
- **修复方案**：兼容字段在 UI 中**默认隐藏**，仅当老用户迁移后首次进入设置时显示一次（提示"已自动迁移"后隐藏），或显示但**禁用点击**（summary 标注"已弃用，请使用上方两项"）

**[UX-P0-2] NumberPickerDialog 最大值 999 过大易导致 OOM**
- **问题**：搜索线程数和更新+缓存线程数的 NumberPickerDialog 范围都是 1-999，用户误输入 999 时每个线程约 1MB 栈空间，999 线程 ≈ 1GB，会直接 OOM 崩溃
- **影响**：用户误操作导致 App 崩溃，且无法预期原因
- **修复方案**：搜索类上限设为 128（与现有 SearchModel 反馈"用户配 32 实际并发 32"语境一致），更新+缓存类上限设为 64（缓存场景并发需求较低）；或统一上限 200

### P1 中等问题（建议修复）

**[UX-P1-1] 配置项缺少影响范围说明**
- **问题**：用户从"搜索线程数"名字无法判断它影响书源搜索/RSS 搜索/换源/换封面/漫画搜索/阅读页搜索/书架搜索/发现页探索/书源校验/RSS 校验/JS 扩展等 11 类业务
- **修复方案**：summary 中列出关键影响业务，例如"控制书源/RSS 搜索、换源换封面、书源校验等场景的并发数，当前: %s"

**[UX-P1-2] 配置变更生效时机不透明**
- **问题**：用户修改搜索线程数后，当前搜索任务继续用旧池，下次搜索才用新池；用户无法感知配置是否生效
- **修复方案**：NumberPickerDialog 确认后 Toast 提示"配置已保存，将在下次搜索时生效"；更新+缓存类提示"配置已立即生效"

**[UX-P1-3] 老用户迁移无提示**
- **问题**：老用户升级后两个新配置自动迁移为旧 threadCount 值，但用户进入设置页看到三个配置项值相同会困惑
- **修复方案**：迁移后首次进入"其他设置"页时弹 Toast"已根据您之前的线程数配置自动迁移为搜索/更新+缓存两个独立配置"

**[UX-P1-4] 默认值差异（32 vs 16）未解释**
- **问题**：搜索默认 32、更新+缓存默认 16，用户不知道为何不同
- **修复方案**：在配置项 dialog 标题或 summary 中标注推荐值，例如"搜索线程数（推荐 32，高性能手机可调高）"

### P2 轻微问题（可选修复）

**[UX-P2-1] 配置项命名"通用线程数（兼容字段）"不够直观**
- **修复方案**：改为"旧版线程数（已弃用）"或直接隐藏

## 二、技术架构角度

### P0 严重问题（必须修复）

**[AR-P0-1] `@Deprecated` 注解默认 level 可能导致编译失败**
- **问题**：Kotlin `@Deprecated` 注解的 `level` 参数默认为 `DeprecationLevel.WARNING`，但若误写为 `ERROR` 会直接阻断编译；同时项目开启了 R8/ProGuard，废弃字段可能被混淆导致反射读取失败
- **影响**：编译失败或运行时 NoSuchFieldError
- **修复方案**：明确使用 `@Deprecated("...", level = DeprecationLevel.WARNING)`；在 `proguard-rules.pro` 中保留 `threadCount` 字段防止混淆

**[AR-P0-2] 老用户迁移条件不健壮**
- **问题**：当前条件 `searchThreadCount == 32 且 threadCount != 32` 判断"是否需要迁移"，但用户可能曾在旧版本改过 threadCount 又改回 32，导致新配置保持默认 32 而非用户期望的值；且迁移标志位检查在 design.md 中描述模糊
- **影响**：迁移误触发或漏触发
- **修复方案**：使用独立的迁移标志位 `pref_migrated_thread_count`（boolean）作为唯一判断条件——首次启动时若标志位不存在则迁移（无论 threadCount 是何值，都将其赋给两个新配置），迁移后写入 true；这样无论 threadCount 是否被改过都正确迁移

**[AR-P0-3] MAX_THREAD 上限移除的 OOM 风险**
- **问题**：AD-08 决策统一去掉所有 `min(threadCount, MAX_THREAD)` 上限，但用户配置 999 时会创建 999 个线程，每个线程栈默认 1MB，总计约 1GB，远超手机可用内存
- **影响**：用户配置过大值直接 OOM 崩溃
- **修复方案**：保留合理上限——搜索类上限 128，更新+缓存类上限 64；或在 NumberPickerDialog 中限制最大值（与 UX-P0-2 一致）；在 `AppConfig.searchThreadCount` setter 中加 `coerceIn(1, 128)` 兜底保护

### P1 中等问题（建议修复）

**[AR-P1-1] "发现页探索"归类依据未在 design.md 充分说明**
- **问题**：MainViewModel.kt L150 `onEachParallel(threadCount)` 用于发现页探索（explore），发现页本质是浏览书源提供的网页列表，与搜索语义不同；归类到搜索类仅因"都是 WebBook 并发请求"
- **修复方案**：在 AD-02 中补充说明"发现页探索与搜索共用 WebBook.exploreBookAwait 接口，且都是用户主动触发的并发请求场景，归搜索类合理"

**[AR-P1-2] MainViewModel 同一文件使用两个不同配置的潜在混淆**
- **问题**：MainViewModel.kt 中 L52-92（upTocPool）用 updateCacheThreadCount，L150（发现页探索）用 searchThreadCount，同一文件混用两个配置可能让后续维护者困惑
- **修复方案**：在代码中添加注释说明"upTocPool 用于书籍目录更新归更新+缓存类，L150 用于发现页探索归搜索类"；在 design.md File Changes 表格中明确标注

**[AR-P1-3] 测试代码使用点未排查**
- **问题**：design.md 仅列出 main 代码的业务点替换，未检查 `app/src/test/` 和 `app/src/androidTest/` 是否有 threadCount 引用
- **修复方案**：实施前 Grep `app/src/test/` 和 `app/src/androidTest/` 确认无遗漏

**[AR-P1-4] BackupConfig 的 ignoreThreadCount 逻辑兼容策略不明确**
- **问题**：design.md 提到"ignoreThreadCount 逻辑兼容两个新 key"，但具体策略未说明——是新增 `ignoreSearchThreadCount` 和 `ignoreUpdateCacheThreadCount` 两个独立 ignore 字段，还是统一沿用 `ignoreThreadCount`？
- **修复方案**：新增两个独立 ignore 字段（`ignoreSearchThreadCount`、`ignoreUpdateCacheThreadCount`），与现有 `ignoreThreadCount` 解耦，让用户备份时可以分别选择是否包含三类配置

**[AR-P1-5] 配置变更与业务读取的时序竞态**
- **问题**：用户修改配置后，正在执行的业务可能读到旧值或新值（取决于读写时机），可能导致线程池大小与配置不一致
- **修复方案**：在文档中说明"配置变更后正在执行的业务不受影响，下次业务启动时使用新配置"——这已是现有 SearchModel 的行为，无需额外处理，但需在 design.md 中明确

### P2 轻微问题（可选修复）

**[AR-P2-1] AppConfig var 属性线程安全性**
- **现状**：现有 `threadCount` 也是 var 非线程安全，本次改造不引入新风险；SharedPreferences 读写本身线程安全
- **修复方案**：保持现状，不额外加 @Synchronized（与现有模式一致）

**[AR-P2-2] 事件总线可靠性**
- **现状**：与现有 threadCount 事件机制一致，不引入新风险
- **修复方案**：保持现状
