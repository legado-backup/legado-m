# Spec: Legado Skill 统一优化重设计

## 1. Intent（意图）

### 1.1 问题陈述
当前 legado-source-creator Skill 存在以下核心问题：
1. **设计文档与实现严重脱节**：legado-skill-optimization 268项任务仅完成5.6%，3套OpenSpec（optimization/usability/v2-rebuild）重叠且均未推进
2. **JVM仿真端兼容性不足**：132个方法中23个不可用（WebView/UI/Rar7z），简单规则可适配但复杂书源/订阅源不兼容
3. **Python客户端工程化缺失**：15个import路径问题、无pyproject.toml、无单元测试、tools/与legado_client/双轨并行
4. **经验知识库不一致**：SKILL.md引用11个不存在文件、references/_INDEX.md缺失5个条目、双写一致性未核验
5. **测试体系形同虚设**：100个新源批量测试0%成功率、无全链路测试规范、错误诊断仅覆盖4种类型
6. **执行偏差严重**：懒原则被滥用规避核心问题、虚假完成项反复出现、子代理输出未校验

### 1.2 目标
1. JAR仿真端+Python客户端与真机合法书源/订阅源高兼容（保真度95%+）
2. 日常开发调试无需频繁查阅源码（经验知识库可检索率>90%）
3. 全流程自动化率>70%（70%网站生成可用源无需手动操作）
4. 端到端测试校验准确性100%（JAR通过则真机通过）

## 2. Scope（范围）

### 2.1 In-Scope（在范围内）
- JVM仿真服务端：源码差距全量盘点与修复、兼容性根因分析、架构优化、性能优化、安卓依赖剥离验证、代码进化机制完善
- Python客户端：工程化体系建设、协同逻辑优化、AI友好性升级、工具集整合
- 经验知识库：双写一致性核验、闭环反哺机制优化
- 测试体系：用例有效性审计、全链路测试规范、错误诊断与自动修复升级、降级机制完善
- 执行偏差复盘：懒原则边界重定义、偏差深度复盘、大型任务上下文管理方案
- 目录结构治理：临时文件清理、废弃代码识别、标准化目录结构

### 2.2 Out-of-Scope（不在范围内）
- Legado App 本身的功能修改
- 新增Legado不支持的功能
- 替代Legado App的完整客户端
- WebView/Selenium渲染引擎差异消除（Chrome桌面 vs Android WebView，已知限制）
- Android原生API模拟（Cronet/Glide/ReadBook单例/Activity Context，已知限制，详见SKILL.md"不实现清单"）

## 3. Approach（方法）

### 3.1 总体策略
采用"审计先行→差距定位→分阶段修复→全量验证"的四阶段策略：
1. 审计先行：前置4项全量核查（已完成）
2. 差距定位：6大专项深度审计（JVM/Python/经验/测试/偏差/目录）
3. 分阶段修复：按P0→P1→P2优先级分3个阶段实施
4. 全量验证：50+50真实源全流程闭环测试

### 3.2 核心原则
1. **源码对标先行**：所有JVM仿真端逻辑修改，必须先对标Legado官方源码确认
2. **真机验证闭环**：JAR测试通过则真机也能通过；JAR失败能准确区分源规则问题还是仿真端问题
3. **经验反哺强制**：测试优化过程中沉淀的所有经验，必须同步更新到references知识库与basic-memory
4. **懒原则边界明确**：仅适用于避免过度工程化，严禁用于规避核心问题、降低验收标准、跳过验证环节

## 4. Requirements（需求）

### 4.1 功能需求

#### REQ-J01: JVM源码差距全量修复
- 逐项比对规则引擎核心能力（AnalyzeRule/JsExtensions/Rhino/jsoup/网络/加密/Cookie/分页/变量持久化）
- 输出差距清单与影响等级，明确补全路径
- 46个可修复方法+21个委托路径全部实现

#### REQ-J02: JVM兼容性根因修复
- 针对"真机可运行的复杂书源/订阅源在仿真端不兼容"的问题，深度定位根因
- 语法支持不全、函数缺失、引擎差异、安卓依赖替换错误等分类修复
- 分阶段修复方案：P0（影响>5%书源）→P1（1-5%）→P2（<1%）

#### REQ-J03: JVM架构优化
- 评估多JAR包拆分vs单一JAR包方案
- 当前已是单一JAR（legado-jvm.jar），确认无需变更
- 性能优化（已完成项）：异步enqueue、JS缓存64、连接池复用、JsExtensionsStub单例
- 性能优化（待优化项）：JVM冷启动预热、批量调试内存管理、JS缓存命中率监控

#### REQ-J04: JVM安卓依赖剥离验证
- 确认JVM端安卓系统依赖剥离完整性
- 排查依赖替换不当导致的逻辑偏差
- 给出补全方案确保核心规则逻辑与安卓端一致

#### REQ-J05: JVM代码进化机制完善
- 优化"触发识别→源码对标→开发补全→验证沉淀"全流程
- 确保JVM功能缺口可被快速闭环修复

#### REQ-P01: Python工程化体系建设
- 新增pyproject.toml/虚拟环境依赖管理规范
- 目录分层架构、模块化接口封装、统一错误处理体系
- 结构化日志输出标准

#### REQ-P02: Python协同逻辑优化
- 明确Python客户端与JVM服务端的职责边界与交互协议
- 覆盖源导入、多阶段测试、错误诊断、结果输出全流程
- 操作逻辑对齐Legado移动端客户端体验

#### REQ-P03: Python AI友好性升级
- 优化测试输出格式
- 失败结果必须包含：错误阶段、根因定位、错误堆栈、对应规则字段指引
- 禁止仅输出"成功/失败"二元结果

#### REQ-P04: Python工具集整合
- 对齐主文件辅助工具清单
- 明确各工具调用场景与降级链路
- 消除tools/与legado_client/功能重叠

#### REQ-E01: 经验知识库双写一致性
- 核查SKILL.md陷阱速查表、references详情库、basic-memory索引层的内容一致性
- 补全缺失条目
- 严格执行权威源规则：Skill文档 > references/ > basic-memory

#### REQ-E02: 经验闭环反哺机制
- 完善"测试发现问题→源码定位根因→沉淀为经验→更新知识库→写入basic-memory"全闭环
- 确保真实测试中的经验可规范沉淀

#### REQ-T01: 测试用例有效性审计
- 区分现有测试用例中有效校验项与空架子项
- 输出保留/优化/删除方案
- 明确每项测试的验证目标与业务价值

#### REQ-T02: 全链路测试规范
- 建立"源导入→规则解析→真实网络请求源站→结果校验→错误诊断"全链路测试流程
- 确保测试结果与真机表现一致

#### REQ-T03: 错误诊断与自动修复升级
- 扩充error_diagnoser与auto_fixer的覆盖场景
- auto_fixer从4种错误类型扩充到12种
- 自动修复成功率>50%

#### REQ-T04: 降级机制完善
- 优化JVM不可用时的Python降级路径
- 确保工作流不中断
- 按标准标注结果可信度等级

### 4.2 非功能需求

#### REQ-NF01: 保真度
- JVM仿真端综合保真度≥95%（当前99.0%按四分类法，但23个不可用方法影响实际兼容性）
- 端到端一致性验证：JAR测试结果与真机运行效果无差异

#### REQ-NF02: 性能
- 单源调试响应时间<10秒
- 批量调试100源完成时间<30分钟

#### REQ-NF03: 可维护性
- 代码变更后JAR重建时间<2分钟
- Python客户端无sys.path动态注入

#### REQ-NF04: 可靠性
- 全流程自动化率>70%
- 自动修复成功率>50%

## 5. Scenarios（场景）

### 5.1 核心场景

#### SC-01: 简单书源创建
用户输入一个笔趣阁类网站URL → Skill自动分析HTML结构 → 生成BookSource JSON → JVM测试通过 → 真机验证一致

#### SC-02: 复杂订阅源创建
用户输入一个视频站URL → 检测到CMS类型 → 复用选择器 → 处理加密视频链接 → 生成RssSource JSON → JVM测试通过

#### SC-03: 书源修复
用户报告"这个源用不了了" → Phase 1查经验 → Phase 4源码深挖 → 修复选择器 → Phase 3测试通过 → Phase 5经验反哺

#### SC-04: 批量源校验
用户导入100个源 → CheckSource批量校验 → 输出每个源的校验结果（通过/失败+原因） → 失败源自动诊断

#### SC-05: JVM降级调试
JVM不可用（JDK缺失） → 自动降级到Python模式 → 搜索+详情阶段可执行 → 结果标注"Python降级模式" → 建议用JAR复验

### 5.2 边界场景

#### SC-06: CF盾网站
网站有CF JS Challenge → loginUrl触发WebView → Python Selenium委托渲染 → Cookie同步 → 后续请求正常

#### SC-07: 加密正文
正文AES-CBC加密 → crypto_analyzer自动分析 → 生成解密代码 → JVM测试通过

#### SC-08: 验证码搜索
搜索需要验证码 → getVerificationCode弹出OCR → 用户输入 → Cookie传递 → 搜索正常
