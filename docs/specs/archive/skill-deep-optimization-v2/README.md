## 功能概述

对 `legado-source-creator` Skill 进行**深度全局审查后的整改优化**，解决**六层系统性问题**：

### 第一层：技术实现层（7 个致命 Bug）

修复 7 个导致"仿真通过但手机报错"的关键 bug：
1. 变量 put/get 两套不互通（跨阶段变量传递失效）
2. getSubDomain 简化错误（多段 TLD Cookie 存错位置）
3. NativeObject/LinkedTreeMap 处理缺失（JS 返回对象解析失败）
4. unescape 缺失（正文残留 HTML 实体）
5. Mode.Regex 缺失（正则规则书源无法解析）
6. type 二进制处理 bug（图片/字体下载返回错误）
7. get/head/post 重定向行为相反

### 第二层：设计哲学层（8 个根本性错误）

1. **目标错位**：把"复刻 Legado"当成了目标，而非"帮助用户生成可用书源"
2. **自进化方向错误**：在进化"仿真服务端"（补全 Mock），而非进化"书源生成能力"（自动修复规则）
3. **测试策略错误**：测试"代码能跑"而非"代码能解决问题"——缺少负面测试
4. **价值层面空架子**：7 个脚本代码能跑但不能解决问题
5. **仿真服务端定位矛盾**：变成了"必须的开发依赖"，而非"可选的测试工具"
6. **造轮子问题**：重新实现了一遍 Legado，而非封装真机 Debug
7. **知识库利用率低**：references/ 有 40+ 文档，但生成书源时很少查阅
8. **"完成"定义错误**：把"代码写完"等同于"任务完成"

### 第三层：价值验证层（3 个根本缺失）

1. **从未验证过 Skill 为用户创造的真实价值**——生成书源的成功率是多少？不知道
2. **从未站在用户角度体验过完整工作流**——一直在"造工具"，从未"用工具"
3. **从未对比过仿真通过 vs 手机可用的成功率**——核心假设从未被验证

### 第四层：用户手工操作过多（10 个核心进化方向 — 用户最新诉求）

> **核心理念**：将"检测到→标记→停止"的消极模式，改为"检测到→尝试辅助→辅助失败再标记"的积极模式，尽可能减少用户手工操作，让用户拿到"手机端导入直接使用"的书源和订阅源。

1. **登录场景主动辅助**（FR-11）：Cookie 导入优先→表单登录辅助→OAuth 标记需人工，三层策略
2. **CF 盾破盾辅助**（FR-12）：cloudscraper 自动求解优先→Cookie 导入降级→UA 指纹优化
3. **验证码识别辅助**（FR-13）：ddddocr OCR 优先→图片导出手动识别降级
4. **加密自动分析**（FR-14）：JS 代码扫描+密钥提取+模式判断+解密代码生成
5. **网站结构智能分析**（FR-15）：CMS 识别+页面结构分析+规则建议+分页识别+反爬识别
6. **错误自动修复**（FR-16）：CSS/URL/字段/语法自动修复+历史方案学习+循环验证
7. **用户交互优化**（FR-17）：交互式登录/CF/验证码引导+规则确认+进度反馈
8. **Cookie/Session 管理增强**（FR-18）：文件持久化+跨网站复用+过期管理+导入导出
9. **网络请求增强**（FR-19）：自适应重试+代理池+频率自适应+UA 池+Referer+日志增强
10. **知识库增强**（FR-20）：网站特征库+解决方案库+自动匹配+自动更新+索引增强

### 第五层：查漏补缺（9 个遗漏项 — 17 条深刻反思对照）

> **核心理念**：用户重新贴出 17 条深刻反思，要求"查漏补缺！不要遗漏任何细节！全方位查漏补缺！"。经逐条对照，发现 9 个遗漏项，归为 5 个需求组（FR-21 到 FR-25）。

1. **设计哲学落地**（FR-21）：脚本用户价值分类（13 个脚本区分"用户受益"vs"AI 自嗨"）+ 仿真服务端模块定位评估 + 高频场景优先策略 + 不实现清单 + 覆盖率策略修正
2. **三 Skill 协作"互相制约"验证**（FR-22）：注入错误验证检查点有效性（auditor 42 检查点检测率 >=80% / workflow 8 检查项检测率 ==100%）+ 防止"互相背书"机制 + 0 命中率检查点标记待评估
3. **质量保障增强**（FR-23）：版本一致性具体化（jsoup/rhino/hutool/okhttp/gson 五版本对比）+ 完成定义检查清单（代码存在/文件修改/功能可用/设计对齐四项验证）+ design.md vs 实际代码一致性 + 异常处理一致性
4. **统一降级链架构**（FR-24）：所有障碍场景（登录/CF/验证码/加密/反爬）遵循统一降级路径：自动求解 → Cookie 导入 → 手动引导 → 标记 unverifiable，降级过程可追踪、可配置
5. **用户体验增强**（FR-25）：工作流耗时统计与瓶颈优化 + 错误信息用户友好化（技术错误→用户语言+修复建议）+ 错误分级（致命/严重/警告/提示四级）+ 进度反馈 + 用户操作最小化检查

### 第六层：真实测试验证优化修复（闭环验证 — 用户最新诉求）

> **核心理念**：前 8 个阶段都是"造工具/修工具"，但没有一个阶段是"用真实源验证工具是否真的能解决问题"。`output/rss/` 目录中已有 6 个真实 RSS 源（覆盖 AES 加密/CF 盾/验证码/视频播放器/苹果 CMS/CookieJar 等场景），必须用这些真实源进行端到端验证，形成"生成→验证→发现问题→优化修复→再验证"的闭环。

1. **真实 RSS 源端到端验证**（FR-26.1）：用 6 个真实 RSS 源（51吃瓜网/小黄书视频/饭团动漫/机房哥视频/18AV视频/1080zyk）逐一执行 debug-source.py
2. **真实书源端到端验证**（FR-26.2）：用 output/book/ 中的真实书源验证 search→detail→toc→content 4 阶段
3. **验证结果分析与问题分类**（FR-26.3）：将问题分为 Bug/规则错误/仿真差距/需用户介入 4 类
4. **基于验证结果的优化修复**（FR-26.4）：针对每类问题进行修复，修复后回归验证通过率 >80%
5. **验证报告输出与经验反哺**（FR-26.5）：输出完整验证报告 + 经验写入 basic-memory 和 references/

### 背景

在 test-infra-upgrade 和 skill-trio-optimization 两个 Spec 实施后，通过深度全局审查发现：

- **仿真服务端与真机差距 40-45%**，其中 7 个是致命级 bug
- **测试脚本 20 个有真实逻辑，但 7 个属"价值层面空架子"**（代码能跑但不能解决用户问题，需提升或废弃）
- **自进化闭环代码存在但未验证**：单元测试 0%、集成测试 0%、回测验证 0%
- **原有设计"必须人工干预边界"过于消极**：登录/CF/验证码场景只是"检测到→标记→停止"，没有主动辅助

### 核心问题诊断

#### 仿真服务端 7 大致命 Bug（"测试通过但手机报错"的真相）

| # | Bug | 根因 | 影响 | 严重度 |
|---|-----|------|------|--------|
| 1 | 变量 put/get 两套不互通 | `java.put()` 存到 MinimalMockJsExtensions.variableMap，`AnalyzeRule.get()` 从 chapter/book/source 取 | 跨阶段变量传递完全失效 | 🔴 致命 |
| 2 | getSubDomain 简化错误 | 用 `parts.takeLast(2)` 替代 PublicSuffixDatabase | 多段 TLD 域名 Cookie 存错位置 | 🔴 致命 |
| 3 | NativeObject/LinkedTreeMap 处理缺失 | spec.md REQ-L6-3 标记完成但实际未实现 | JS 返回对象时规则解析行为不同 | 🔴 致命 |
| 4 | unescape 缺失 | 真机 getString 最后有 `StringEscapeUtils.unescapeHtml4`，仿真没有 | 正文残留 HTML 实体（&amp; &#x; 等） | 🔴 致命 |
| 5 | Mode.Regex 缺失 | 仿真版 AnalyzeRule 无 AnalyzeByRegex | 使用正则规则的书源无法正确解析 | 🔴 致命 |
| 6 | type 非空处理 bug | 二进制类型 URL 两个分支都走 executeStrRequest | 图片/字体下载返回错误 | 🟠 严重 |
| 7 | get/head/post 重定向行为相反 | 仿真 followRedirects(true)，真机 followRedirects(false) | 依赖重定向拦截的书源行为不同 | 🟠 严重 |

## 设计原则

1. **源码优先**：所有 bug 修复必须对照真机源码，禁止臆测
2. **行为一致**：修复后必须用真机日志对比验证
3. **真实回测**：禁止用 mock 数据回测，必须用真实网站
4. **文档同步**：每个修复必须同步更新设计文档和 SKILL.md
5. **懒原则**：只修复致命和严重 bug，不追求 100% 覆盖率
6. **积极辅助优先**：检测到障碍时，先尝试主动辅助，辅助失败再标记需人工（新增）
7. **高频场景优先**：只补齐影响 >5% 书源的功能，不追求 100% 函数覆盖率（新增）
8. **互相制约**：三 Skill 协作必须双向制约，通过注入错误验证检查点有效性（新增）
9. **统一降级**：所有障碍场景遵循统一降级链，降级过程可追踪、可配置（新增）
