# Spec: Skill 深度优化 V2 — 仿真服务端关键 Bug 修复 + 设计哲学修正 + 价值验证落地 + 减少用户手工操作 + 查漏补缺 + 真实测试验证优化修复

---

## 1. Intent（意图）

### 1.1 问题陈述

test-infra-upgrade 和 skill-trio-optimization 两个 Spec 实施后，通过深度全局审查发现**六层系统性问题**：

**第一层：技术实现层**（7 个致命 bug）
- 代码实现存在 7 个致命级 bug，导致仿真服务端与真机行为差距 40-45%
- 根因是实施过程中"偷懒"和"自以为是"——设计文档写得很清楚，但实际实现时走了捷径

**第二层：设计哲学层**（8 个根本性错误）
1. **目标错位**：把"复刻 Legado"当成了目标，而非"帮助用户生成可用书源"——以"函数覆盖率"为导向，而非"用户使用频率"为导向
2. **自进化方向错误**：在进化"仿真服务端"（补全 Mock），而非进化"书源生成能力"（自动修复规则）——进化终点是"Mock 补全了"，而非"用户的问题解决了"
3. **测试策略错误**：测试"代码能跑"而非"代码能解决问题"——缺少负面测试，只测 happy path
4. **价值层面空架子**：7 个脚本代码能跑但不能解决问题（speed_metrics/evolution_trigger/evolution_convergence/auto_evolve_server/generate-js-doc/deep-analyze-js/check_*.py）
5. **仿真服务端定位矛盾**：变成了"必须的开发依赖"，而非"可选的测试工具"——JVM 不可用时整个 5 阶段工作流就断了
6. **造轮子问题**：重新实现了一遍 Legado，而非封装真机 Debug——维护成本高、一致性难保证
7. **知识库利用率低**：references/ 有 40+ 文档，但生成书源时很少查阅——知识库与代码脱节
8. **"完成"定义错误**：把"代码写完"等同于"任务完成"——真正的完成应该是"代码+测试+文档+回测"

**第三层：价值验证层**（3 个根本缺失）
1. **从未验证过 Skill 为用户创造的真实价值**——用户用这个 Skill 生成书源的成功率是多少？不知道
2. **从未站在用户角度体验过完整工作流**——一直在"造工具"，从未"用工具"
3. **从未对比过仿真通过 vs 手机可用的成功率**——"仿真通过=手机可用"这个核心假设从未被验证

**第四层：用户手工操作过多**（10 个核心进化方向）
1. **原有设计"必须人工干预边界"过于消极**——检测到登录/CF/验证码等障碍时只是"标记→停止"，没有主动辅助
2. **缺少登录辅助/CF 破盾/验证码识别/加密自动分析/网站结构分析/错误自动修复等主动辅助能力**
3. **Cookie 管理仅内存版**——JVM 重启后丢失，用户需重新登录
4. **网络请求过于简单**——容易触发限流/IP 封禁
5. **知识库被动查阅**——遇到新网站从零开始，无自动匹配

**第五层：查漏补缺**（9 个遗漏项 — 17 条深刻反思对照）
1. **缺少脚本用户价值分类**——13 个脚本未区分"用户受益"vs"AI 自嗨"
2. **缺少 CLI 封装 vs 重新实现评估**——5 个核心模块定位未评估
3. **缺少不实现清单**——未明确"不实现什么"，存在 scope creep 风险
4. **版本一致性检查太简略**——FR-8.3 只提"检查"未具体化
5. **缺少完成定义检查清单**——"完成"无四项验证
6. **缺少错误信息用户友好翻译**——技术错误未翻译为用户语言
7. **三 Skill 协作"互相背书"问题**——检查点有效性从未验证
8. **缺少统一降级链架构**——各障碍场景独立处理，无统一降级路径
9. **缺少工作流耗时优化**——5 阶段耗时未统计，瓶颈未识别

**第六层：真实测试验证优化修复**（闭环验证 — 用户最新诉求）
1. **前 8 个阶段都是"造工具/修工具"**——没有一个阶段是"用真实源验证工具是否真的能解决问题"
2. **output/rss/ 目录中已有 6 个真实 RSS 源**（覆盖 AES 加密/CF 盾/验证码/视频播放器/苹果 CMS/CookieJar 等场景），必须用这些真实源进行端到端验证
3. **缺少"生成→验证→发现问题→优化修复→再验证"的闭环**——修复后回归验证通过率需 >80%

### 1.2 目标

**第一层目标（技术实现）**：
1. 修复 7 个致命 bug，使仿真服务端与真机一致率从 ~60% 提升到 >90%

**第二层目标（设计哲学修正）**：
2. 自进化方向从"补全 Mock"转向"自动修复书源规则"
3. 测试策略从"证明代码能跑"转向"证明代码能解决问题"（补充负面测试）
4. 清理 7 个价值层面空架子（提升或废弃）
5. 仿真服务端从"必须依赖"降为"可选工具"（JVM 不可用时工作流不中断）
6. 知识库强制查阅机制（生成书源时必须搜索 references/）

**第三层目标（价值验证）**：
7. 用真实书源/订阅源回测，验证"仿真通过=手机可用"
8. 端到端体验完整 5 阶段工作流，验证用户体验
9. 错误信息可操作性提升（仿真失败时给出修复建议）

**第四层目标（减少用户手工操作）**：
10. 登录/CF/验证码/加密/网站结构/错误修复等场景从"消极标记"转为"积极辅助"
11. Cookie 跨会话持久化，网络请求自适应，知识库主动匹配
12. 全流程自动化率 >70%（70% 网站无需用户手工操作即可生成可用书源/订阅源）

**第五层目标（查漏补缺）**：
13. 13 个脚本按用户价值分类，高频场景优先，不实现清单防止 scope creep
14. 三 Skill 协作从"互相背书"改为"互相制约"（注入错误验证检查点有效性）
15. 版本一致性检查具体化，完成定义检查清单四项验证

**第六层目标（真实测试验证优化修复）**：
16. 用 6 个真实 RSS 源 + 1 个真实书源进行端到端闭环验证
17. 验证发现问题→分类→修复→回归验证→经验反哺，回归通过率 >80%

### 1.3 非目标

- ❌ 不追求 100% 函数覆盖率（JsExtensions 120+ 函数只补齐高频项）
- ❌ 不重写仿真服务端架构（在现有基础上修复）
- ❌ 不改变 5 阶段工作流
- ❌ 不实现 BackstageWebView 仿真（保持 unverifiable 标记）
- ❌ 不实现 ADB 连接真机方案（后续 Spec 考虑）
- ❌ 不废弃自进化闭环（修正方向而非删除）

## 3. Approach（方法）

### 3.1 总体策略

**先修致命 bug，再整改基础设施，最后补齐测试验证**。

```
阶段一：修致命 bug（P0）
  ├─ 1.1 变量 put/get 层级存储修复
  ├─ 1.2 getSubDomain 修复
  ├─ 1.3 NativeObject/LinkedTreeMap 处理补齐
  ├─ 1.4 unescape 补齐
  ├─ 1.5 Mode.Regex 补齐
  ├─ 1.6 type 二进制处理修复
  └─ 1.7 重定向行为修复

阶段二：整改基础设施（P1）
  ├─ 2.1 孤儿脚本索引 + 合并
  ├─ 2.2 deep-verify.py 废弃决策修正
  ├─ 2.3 函数名对齐设计文档
  ├─ 2.4 硬编码路径修复
  ├─ 2.5 stub mock 行为验证
  └─ 2.6 speed_metrics 自动埋点

阶段三：补齐测试验证（P0）
  ├─ 3.1 单元测试编写（4 个模块）
  ├─ 3.2 集成测试编写（5 个场景）
  └─ 3.3 真实书源/订阅源回测（5 个用例）
```

### 3.2 设计约束

| 约束 | 值 | 说明 |
|------|-----|------|
| 仿真服务端与真机一致率 | >90% | 修复 7 个致命 bug 后 |
| 单元测试覆盖率 | >70% | 4 个核心模块 |
| 集成测试覆盖率 | >60% | 5 个场景 |
| 真实回测用例数 | 5 个 | 3 书源 + 2 订阅源 |
| SKILL.md 行数 | <500 | 整改后 |
| 函数名与设计文档一致率 | 100% | 全部对齐 |

### FR-4: 自进化方向修正（P0）

> **核心反思**：自进化进化的方向是"仿真服务端"（补全 Mock）而非"书源生成能力"（自动修复规则）。进化终点是"Mock 补全了"而非"用户的问题解决了"。

| ID | 需求 | 验收标准 |
|----|------|---------|
| FR-4.1 | evolution_trigger.py 新增"书源规则修复"分类：当根因为 rule_error 时，自动分析规则错误并给出修复建议（而非补全 Mock） | rule_error 类型的错误能给出具体修复建议 |
| FR-4.2 | classify-and-fix.py 实现真正的 fix：自动修改源 JSON 并重新验证（当前只输出建议字符串） | 修复后的源 JSON 能通过 debug-source.py 验证 |
| FR-4.3 | 自进化闭环终点修正：从"Mock 补全"改为"书源规则修复成功或给出明确修复建议" | 进化日志记录的是"规则修复结果"而非"Mock 补全结果" |

### FR-5: 负面测试补齐（P0）

> **核心反思**：测试策略缺少"负面测试"——只测能通过的（happy path），不测应该失败的（unhappy path）。真正能反映问题的测试应该是"故意制造错误的测试"。

| ID | 需求 | 验收标准 |
|----|------|---------|
| FR-5.1 | 负面测试：故意写错 ruleToc 的书源，验证仿真能检测到"目录阶段失败" | 仿真输出明确的"目录阶段失败"错误信息 |
| FR-5.2 | 负面测试：需要登录的网站，验证 site_type_detector 能识别并提示"需手动登录" | 输出"该网站需要登录，建议手动处理" |
| FR-5.3 | 负面测试：有 CF 保护的网站，验证 site_type_detector 能识别并标记"需真机验证" | 输出"该网站有 CF 保护，仿真结果仅供参考" |
| FR-5.4 | 负面测试：故意写错 CSS 选择器，验证仿真能检测到"选择器未匹配到元素" | 输出"选择器 .xxx 未匹配到任何元素，请检查" |
| FR-5.5 | 负面测试：故意写错加密参数，验证 verify-decrypt.py 能检测到"解密失败" | 输出"解密失败，请检查 key/iv/algo 参数" |

### FR-6: 价值层面空架子清理（P1）

## 5.5 减少用户手工操作（核心进化方向 — 用户最新诉求）

> **背景**：用户明确指出"你现在做的这个设计是为了优化skill，这个skill还是优化后你为了帮助用户去为了用户生成优化书源和订阅源的，你要考虑的问题永远都是尽可能的完成整个网站的分析，生成工作，如果真的需要用户手工操作的话，你得想想办法"。
>
> **原有设计的根本性遗漏**：skill-trio-optimization FR-10（必须人工干预边界）+ test-infra-upgrade 场景2/3 + 本 Spec FR-5.2/5.3 都是"检测到→标记→停止"的消极模式，**完全没有主动辅助能力**。用户期望的是"检测到→尝试辅助→辅助失败再标记"的积极模式。
>
> **核心原则**：减少用户手工操作 ≠ 完全替代用户。对于信任边界场景（账号密码登录、人工验证码），AI 不应替代用户操作，但应**尽可能辅助用户完成**（如引导用户提供 Cookie、自动求解 CF Challenge、OCR 识别简单验证码等）。

## 5. Scenarios（场景）

### 场景 1: 变量跨阶段传递验证（FR-1.1 修复后）

**输入**：书源 ruleBookInfo.init 含 `java.put("tocUrl", "https://example.com/toc")`，ruleToc.tocUrl 含 `@get:{tocUrl}`

**验收**：目录页 URL 正确构造，目录阶段能获取章节列表。
