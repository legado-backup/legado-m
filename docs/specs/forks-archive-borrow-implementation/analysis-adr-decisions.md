## 2. 18 个 ADR 逐项深度评估

### 2.1 ADR-001 三阶段实施策略（P0→P1→P2）

- **Status**：Accepted
- **Context 准确性**：✅ 通过
  - 准确识别了"54 项决策跨 6 大模块、用户价值区间 2.8-5.0、实施成本跨度大（低/中/高）"的核心矛盾
  - 准确列出了"一次性全部实施风险集中、只实施 P0 遗漏中高收益项、无序实施效率低"三大问题
- **Decision 合理性**：✅ 通过
  - P0（10 项，用户价值 4.5-5.0，本周内启动）：聚焦用户核心场景
  - P1（23 项，中高收益 17 项 + 开发者侧 6 项，季度内）：覆盖中高收益
  - P2（21 项，技术升级 5 项 + 中价值 7 项 + UI 优化 9 项，年度内）：长期价值
  - 三阶段切分符合"用户价值优先 + 风险分散"原则
- **Consequences 完整性**：✅ 通过
  - 正向：风险分散、用户最快感知收益、进度可追踪
  - 负向：整体跨度 12 个月、P2 UI 优化延后影响长期体验
- **Alternatives 充分性**：✅ 通过
  - 备选 A（一次性全部实施）→ 否决理由充分（>6 个月、回归测试过大）
  - 备选 B（只实施 P0）→ 否决理由充分（遗漏 P1 中高收益项）
  - 备选 C（无序实施）→ 否决理由充分（资源浪费）
- **Drawbacks 识别**：✅ 通过
  - 识别了"分阶段周期长、P2 优先级可能随用户反馈调整"两个核心缺点
- **建议**：保持原样
- **理由**：三阶段策略是整个项目的实施骨架，决策合理、备选充分、Consequences 完整。已在 ADR-002 中细化 P0 内部并行策略，整体闭环。

  - 备选 B（仅用单维度）→ 否决理由充分（无法体现核心场景权重）
- **Drawbacks 识别**：✅ 通过
  - 识别了"评分主观性存在"缺点，并给出了"每个维度明确 1-5 分评分细则"的缓解措施
- **建议**：保持原样
- **理由**：四维度评估标准是整个项目决策的基石，权重分配合理、决策规则清晰。已成功应用于 v5.0 终版决策，验证了有效性。

### 2.7 ADR-007 RSS 搜索增强双轨方案

- **Status**：Accepted
- **Context 准确性**：✅ 通过
  - 准确识别了"RssSource 实体已有 searchUrl 字段但没有任何 Activity/Fragment 使用它"的关键事实
  - 准确评估了借鉴投入产出比极高（1 个 Activity + 5 行入口代码）
- **Decision 合理性**：✅ 通过
  - 双轨方案清晰：数据轨（复用已有字段，零数据变更）+ UI 轨（新增 Activity/ViewModel/Adapter/Fragment 入口）
  - 用户价值 5.0（最高）与实施成本（低）的投入产出比合理
- **Consequences 完整性**：✅ 通过
  - 正向：数据零变更降低风险、UI 入口补全激活能力、用户价值 5.0（最高）
  - 负向：新增 3 个文件需测试覆盖
- **Alternatives 充分性**：✅ 通过
  - 备选 A（在现有 SearchActivity 中扩展）→ 否决理由充分（架构耦合，违反单一职责）
  - 备选 B（等待 Archive 完整 DiscoverySuite 套件 130KB+）→ 否决理由充分（体量过大与极简哲学冲突）
- **Drawbacks 识别**：✅ 通过
  - 识别了"新增 3 个文件"缺点，并给出了"配套单元测试覆盖搜索/分页/异常"的缓解措施
- **建议**：保持原样
- **理由**：双轨方案充分利用已有数据字段，零数据变更降低风险，UI 入口补全激活能力，是 P0 中投入产出比最高的任务。

### 2.9 ADR-009 EPUB 渲染引擎不替换

- **Status**：Accepted
- **Context 准确性**：✅ 通过
  - 准确列出了差距（Archive 46 文件 16000+ 行 vs 本项目 1 个 EpubFile.kt ~700 行，差距 23 倍）
  - 准确识别了 Archive 偏离本项目"书源规则引擎"主航道、工程量过大
  - 准确提取了 Archive 优秀设计范式（Book.kt 实体零扩展原则）
- **Decision 合理性**：✅ 通过
  - EPUB 渲染引擎不替换，仅借鉴部分小特性（P0 2 项、P1 4 项、P2 6 项）
  - 明确设计原则：所有 EPUB 增强遵守 Book.kt 实体零扩展原则，缓存数据走独立磁盘目录
- **Consequences 完整性**：✅ 通过
  - 正向：保持本项目主航道清晰、避免大规模架构调整、渐进式优化降低风险
  - 负向：EPUB 渲染能力长期落后 Archive（用户接受此代价）
- **Alternatives 充分性**：✅ 通过
  - 备选 A（整体借鉴 16000+ 行）→ 否决理由充分（偏离主航道，工程量过大）
  - 备选 B（自研 EPUB 渲染引擎）→ 否决理由充分（重复造轮子，资源浪费）
- **Drawbacks 识别**：✅ 通过
  - 识别了"EPUB 渲染能力落后"缺点，并给出了"渐进式借鉴 10 项低风险优化"的缓解措施
- **建议**：保持原样
- **理由**：不替换 EPUB 引擎符合极简哲学与主航道原则，渐进式借鉴策略合理，Book.kt 实体零扩展原则为后续实施提供了清晰约束。

## 3. 遗漏的 ADR 识别

### 3.1 重要遗漏

#### 3.1.1 🔴 高优先级遗漏

##### ADR-019 网络安全与隐私策略（建议新增）

- **遗漏原因**：
  - RSS-B-01 多源并发搜索会向多个站点发起请求，可能泄露用户 IP 与搜索关键词
  - THEME-B-07 主题包云端同步涉及用户主题数据上传到云端
  - VIDEO 模块视频播放涉及视频源 URL 与播放记录
  - 缺乏统一的 HTTPS/SSL/TLS 配置策略、用户数据加密策略、隐私协议策略
- **Context**：54 项任务中多项涉及网络请求与用户数据上传，但缺乏统一的网络安全与隐私保护策略
- **Decision（建议）**：
  1. **HTTPS 强制**：所有网络请求优先使用 HTTPS，HTTP 请求需用户显式确认
  2. **用户数据加密**：主题包云端同步前必须本地加密，密钥由用户密码派生
  3. **隐私协议**：首次启动时提示用户隐私协议，明确数据收集范围
  4. **日志脱敏**：日志中禁止记录完整 URL、cookie、token 等敏感信息
  5. **网络层超时**：所有网络请求设置 30s 超时，避免长时间阻塞
- **Consequences**：
  - 正向：保护用户隐私、符合应用商店合规要求、降低法律风险
  - 负向：增加开发成本（约 2-3 人天）、可能影响部分 RSS 源兼容性
- **Alternatives**：
  - 备选 A：不实施隐私策略 → 否决（违反应用商店合规要求）
  - 备选 B：仅在 P2 实施隐私策略 → 否决（P0 RSS 搜索已涉及网络请求）
- **Drawbacks**：增加开发成本；缓解措施：复用现有网络安全组件
- **优先级**：高（P0 实施前必须确立）

##### ADR-020 性能预算策略（建议新增）

- **遗漏原因**：
  - ADR-016 定义了性能基准测试方法学，但未定义性能预算上限
  - 缺少启动时间、内存占用、APK 体积上限的明确约束
  - ADR-004 仅约束 UI 优化类包体积增长 ≤ 5MB，但未覆盖整体 APK 体积上限
- **Context**：54 项任务完成后，APK 体积、启动时间、内存占用可能显著增长，需建立性能预算上限
- **Decision（建议）**：
  1. **APK 体积上限**：整体 APK 体积 ≤ 当前 + 10MB（含 UI 优化 5MB + 其他 5MB）
  2. **启动时间上限**：冷启动时间 ≤ 当前 + 10%
  3. **内存占用上限**：峰值内存 ≤ 当前 + 50MB
  4. **FPS 下限**：阅读翻页 FPS ≥ 50，视频播放 FPS ≥ 30
  5. **搜索响应上限**：RSS 搜索 < 3s（5 源并发）
- **Consequences**：
  - 正向：性能可量化可对比、避免性能退化、为优化提供目标
  - 负向：部分借鉴点可能因性能预算无法实施
- **Alternatives**：
  - 备选 A：不设性能预算 → 否决（性能退化无法及时发现）
  - 备选 B：仅设 APK 体积上限 → 否决（启动时间/内存同样重要）
- **Drawbacks**：部分借鉴点可能因预算无法实施；缓解措施：超预算时优先保留高用户价值项
- **优先级**：高（P0 实施前必须确立）

##### ADR-021 错误处理与异常上报统一策略（建议新增）

- **遗漏原因**：
  - ADR-015 协程调度策略仅覆盖了协程错误处理（Coroutine.onError）
  - 缺少业务异常分类、用户提示策略、异常上报策略的统一说明
  - 54 项任务中多项可能产生业务异常（如 RSS 搜索失败、视频加载失败、EPUB 解析失败、主题包导入失败等）
- **Context**：54 项任务中多个涉及网络请求、文件解析、数据库操作，可能产生各类业务异常，需统一错误处理策略
- **Decision（建议）**：
  1. **异常分类**：业务异常（NoStackTraceException 子类）+ 网络异常 + IO 异常 + 数据库异常
  2. **用户提示**：可恢复异常显示 Toast，不可恢复异常显示 Dialog 并提供重试选项
  3. **异常上报**：异常通过 AppLog.put() 记录到本地日志，禁止上报到第三方服务（隐私保护）
  4. **异常隔离**：单源/单文件/单章节失败不影响整体功能，错误信息收集后统一展示
  5. **回退策略**：关键功能（如 EPUB 渲染）失败时回退到简化模式
- **Consequences**：
  - 正向：用户体验一致、异常可追踪、不影响整体功能
  - 负向：增加异常处理代码量
- **Alternatives**：
  - 备选 A：不统一错误处理 → 否决（用户体验不一致，难以排查问题）
  - 备选 B：使用第三方异常上报服务 → 否决（违反隐私保护原则）
- **Drawbacks**：增加异常处理代码量；缓解措施：建立异常处理工具类
- **优先级**：高（P0 实施前必须确立）

#### 3.1.2 🟡 中优先级遗漏

##### ADR-022 兼容性策略（建议新增）

- **遗漏原因**：
  - 项目 minSdk 已提升至 23，但部分新增依赖可能要求 API 24+
  - 如 rhino 1.8.1 锁定原因之一是 API 24 以下缺少 Arrays.setAll
  - liquidglass 1.0.3、lottie 6.6.6 等新增依赖的 minSdk 兼容性未明确
  - 屏幕适配（如 Compose 列表、FlexboxLayout）未明确
- **Context**：54 项任务中多个涉及新增依赖与 UI 适配，需统一兼容性策略
- **Decision（建议）**：
  1. **minSdk 锁定**：minSdk 23 不变，所有新增依赖必须支持 API 23+
  2. **API 级别检查**：使用 @RequiresApi 注解 + 运行时版本判断
  3. **屏幕适配**：所有新增 UI 适配 4.5-10 寸屏幕，支持横竖屏
  4. **依赖兼容性验证**：新增依赖引入前必须验证 minSdk 兼容性
- **Consequences**：
  - 正向：保证低版本设备兼容性、避免崩溃
  - 负向：部分新特性无法使用
- **Alternatives**：
  - 备选 A：提升 minSdk 至 24 → 否决（影响现有用户）
  - 备选 B：不验证依赖兼容性 → 否决（运行时崩溃风险）
- **Drawbacks**：部分新特性无法使用；缓解措施：使用降级方案
- **优先级**：中

##### ADR-023 日志策略（建议新增）

- **遗漏原因**：
  - ADR-015 仅说明了"异常用 Coroutine.onError 捕获后用 AppLog.put() 记录"
  - 但日志级别、日志保留策略、日志上报策略、用户隐私保护未明确
  - 项目规范 logging-during-refactoring.md 要求"改造过程日志记录"，但缺乏统一日志策略
- **Context**：54 项任务中多个涉及日志记录，需统一日志策略避免日志泛滥与隐私泄露
- **Decision（建议）**：
  1. **日志级别**：DEBUG（开发期）/ INFO（关键流程）/ WARN（异常可恢复）/ ERROR（异常不可恢复）
  2. **日志工具**：统一使用 AppLog.put()，禁止 android.util.Log.d/e
  3. **日志保留**：本地日志保留 7 天，超期自动清理
  4. **日志脱敏**：禁止记录完整 URL、cookie、token、用户密码等敏感信息
  5. **日志上报**：仅本地存储，禁止自动上报到第三方服务
- **Consequences**：
  - 正向：日志规范统一、便于排查问题、保护用户隐私
  - 负向：增加日志管理代码
- **Alternatives**：
  - 备选 A：使用 Timber → 否决（项目规范明确禁止）
  - 备选 B：不统一日志策略 → 否决（日志泛滥，难以排查）
- **Drawbacks**：增加日志管理代码；缓解措施：建立日志工具类
- **优先级**：中

##### ADR-024 测试覆盖率策略（建议新增）

- **遗漏原因**：
  - ADR-012 仅说明真机测试强制流程，未定义单元测试覆盖率要求
  - ADR-016 仅说明性能基准测试，未定义功能测试覆盖率
  - 54 项任务中新增多个工具类（如 PaperInkHelper、VideoBookPreloader、SearchBookMergeUtils 等），需明确单元测试覆盖率要求
- **Context**：54 项任务中新增多个工具类与业务逻辑，需明确测试覆盖率策略保证代码质量
- **Decision（建议）**：
  1. **单元测试覆盖率**：新增工具类单元测试覆盖率 ≥ 80%
  2. **集成测试**：每个模块至少 1 个集成测试场景
  3. **真机测试**：每个 P 阶段完成后必须真机测试（已在 ADR-012 约束）
  4. **回归测试**：P2 完成后全量回归测试
  5. **测试工具**：JUnit + Mockito + ai_tests/scripts/
- **Consequences**：
  - 正向：代码质量有保证、问题早发现
  - 负向：增加测试开发工作量
- **Alternatives**：
  - 备选 A：不要求覆盖率 → 否决（无法保证测试质量）
  - 备选 B：覆盖率 ≥ 95% → 否决（成本过高，部分 UI 代码难以测试）
- **Drawbacks**：增加测试开发工作量；缓解措施：优先测试核心业务逻辑
- **优先级**：中

##### ADR-025 发布策略（建议新增）

- **遗漏原因**：
  - 54 项任务分三阶段实施，但未定义版本号管理、灰度发布、回滚策略
  - ADR-011 仅说明文档同步，未说明版本号与发布流程
- **Context**：54 项任务分三阶段实施，每个阶段完成后需发布版本，需统一发布策略
- **Decision（建议）**：
  1. **版本号**：采用语义化版本号（Major.Minor.Patch），P0/P1/P2 各对应一个 Minor 版本
  2. **灰度发布**：每个版本先内部测试 → 灰度 10% → 灰度 50% → 全量
  3. **回滚策略**：每个版本发布后保留回滚能力（保留旧版本 APK）
  4. **发布渠道**：GitHub Release + Gitee 镜像同步
  5. **发布前检查**：编译通过 + 真机测试通过 + 文档同步 + 性能基准达标
- **Consequences**：
  - 正向：版本演进可追踪、问题可回滚、用户体验稳定
  - 负向：增加发布管理工作量
- **Alternatives**：
  - 备选 A：不灰度直接全量发布 → 否决（问题影响所有用户）
  - 备选 B：不保留回滚能力 → 否决（问题无法快速恢复）
- **Drawbacks**：增加发布管理工作量；缓解措施：使用 CI 自动化发布
- **优先级**：中

#### 3.1.3 🟢 低优先级遗漏

  1. **代码审查**：所有代码变更必须经过自审 + 交叉审查
  2. **静态分析**：使用 Detekt 进行 Kotlin 静态分析

  4. **代码风格**：遵循项目命名规范与 checkstyle_rules.md

  - 正向：代码质量保证、潜在问题早发现
  - 负向：增加代码审查工作量
- **优先级**：低

##### ADR-027 用户反馈策略（建议新增）

## 4. ADR 之间冲突检查

### 4.1 已识别冲突

#### 4.1.1 ADR-002（P0 分组并行）vs ADR-012（真机测试强制）

- **冲突描述**：
  - ADR-002 采用 4 个并行组执行 P0 10 项任务，工期从 10-15 人天缩短至 6-10 人天
  - ADR-012 要求"每个 P 阶段完成后必须按 ai_e2e_testing_workflow.md 执行真机测试"
  - 并行组间合并后真机测试可能因冲突难以定位问题根因
- **冲突等级**：🟡 中等
- **解决方案**：
  1. 每个并行组完成组内任务后先进行组内 L1 验证（quick_build_install.py）
  2. 4 个并行组全部合并后再进行全量真机测试（run_e2e.py --tc all）
  3. 若全量测试失败，使用 git bisect 定位问题引入点
  4. 在 ADR-002 中补充"组间合并前 Grep 校验冲突"的检查点

#### 4.1.2 ADR-003（AI 模块全量否决）vs ADR-005（用户价值评估）

- **冲突描述**：
  - ADR-003 全量否决 AI 模块 11 项决策
  - ADR-005 用户价值评估四维度标准中"用户额外负担"权重 10%，AI 模块因需 API key 减分
  - 严格按 ADR-005 评估，AI 模块中部分项（如 MCP 客户端 420 行可独立移植）用户价值可能在 3.5-3.9 之间，应降级为 P2 而非全量否决
- **冲突等级**：🟢 轻微（用户已明确反对）
- **解决方案**：
  - ADR-003 已明确用户反馈"AI 模块，我都不建议加入到我的项目中去"
  - 用户反馈优先级高于 ADR-005 评分规则
  - 在 ADR-003 中补充说明"用户反馈优先级高于用户价值评分，AI 模块即使用户价值评分达标也保持否决"

#### 4.1.3 ADR-006（锁定依赖不升级）vs ADR-014（网络层兼容性）

- **冲突描述**：
  - ADR-006 锁定 10 项核心依赖不升级（包括 webkit 1.14.0、room 2.7.1 等）
  - ADR-014 要求"pureSearch 向后兼容"、"复用本项目已有 Semaphore 限流"
  - 锁定依赖可能限制 pureSearch 实现方式（如无法使用新版本 webkit API）
- **冲突等级**：🟢 轻微
- **解决方案**：
  - ADR-014 已明确"复用本项目已有 Semaphore 限流"，不涉及新依赖
  - pureSearch 是 RssSource 字段控制，不涉及 webkit API 升级
  - 在 ADR-014 中补充说明"pureSearch 实现不依赖锁定依赖之外的版本"

#### 4.1.4 ADR-009（EPUB 引擎不替换）vs ADR-013（数据库迁移安全）

- **冲突描述**：
  - ADR-009 EPUB 渲染引擎不替换，仅借鉴部分小特性（P0 2 项、P1 4 项、P2 6 项）
  - ADR-013 数据库迁移安全策略针对 THEME-B-04 Config 字段扩展与 VIDEO-E-01 ReadRecentBook 写入
  - EPUB 模块不涉及数据库 schema 变更，ADR-013 对 EPUB 模块无约束
- **冲突等级**：🟢 轻微（实际无冲突）
- **解决方案**：
  - ADR-009 与 ADR-013 适用范围不同，无直接冲突
  - 在 ADR-013 中明确"本策略仅针对涉及数据库 schema 变更的任务（THEME-B-04、VIDEO-E-01），EPUB 模块不涉及"

#### 4.1.5 ADR-015（协程调度统一）vs ADR-016（性能基准）

- **冲突描述**：
  - ADR-015 要求所有异步操作使用 Coroutine.async{}...onError{}.onSuccess{} 链式封装
  - ADR-016 要求性能基准测试，容忍阈值启动时间 +5%、FPS -3 帧
  - 链式封装可能引入额外性能开销（如 Coroutine 对象创建）
- **冲突等级**：🟢 轻微
- **解决方案**：
  - 链式封装的性能开销在 ms 级，远低于容忍阈值
  - 在 ADR-016 中补充说明"性能基准测试容忍链式封装的性能开销"
  - 若性能基准测试发现链式封装导致显著性能退化，可在 ADR-015 中补充"性能敏感场景允许使用标准 launch"

## 6. ADR 合并/拆分建议

### 6.1 可合并的 ADR

#### 6.1.1 合并方案 1：ADR-011 + ADR-012 → ADR-011 任务完成强制流程

- **合并理由**：
  - ADR-011（文档同步与版本交付）与 ADR-012（真机测试强制流程）均为"任务完成后的强制流程"

- **合并后 ADR-011 任务完成强制流程**：
  - 每个 P 阶段完成后必须执行：

    4. **问题记录**：所有问题记录到 issues-found.md

### 6.2 需拆分的 ADR

#### 6.2.1 拆分方案 1：ADR-010 → ADR-010a + ADR-010b

- **拆分理由**：

    - 回退策略：同步失败时保留本地版本，提示用户重试

### 7.2 详细新增 ADR

#### 7.2.1 ADR-019 网络安全与隐私策略

- **Status**：Proposed
- **Context**：54 项任务中 RSS-B-01 多源并发搜索向多个站点发起请求可能泄露用户 IP 与搜索关键词；THEME-B-07 主题包云端同步涉及用户主题数据上传到云端；VIDEO 模块视频播放涉及视频源 URL 与播放记录。缺乏统一的 HTTPS/SSL/TLS 配置策略、用户数据加密策略、隐私协议策略。
- **Decision**：
  1. **HTTPS 强制**：所有网络请求优先使用 HTTPS，HTTP 请求需用户显式确认
  2. **用户数据加密**：主题包云端同步前必须本地加密，密钥由用户密码派生
  3. **隐私协议**：首次启动时提示用户隐私协议，明确数据收集范围
  4. **日志脱敏**：日志中禁止记录完整 URL、cookie、token 等敏感信息
  5. **网络层超时**：所有网络请求设置 30s 超时，避免长时间阻塞
- **Consequences**：
  - 正向：保护用户隐私、符合应用商店合规要求、降低法律风险
  - 负向：增加开发成本（约 2-3 人天）、可能影响部分 RSS 源兼容性
- **Alternatives**：
  - 备选 A：不实施隐私策略 → 否决（违反应用商店合规要求）
  - 备选 B：仅在 P2 实施隐私策略 → 否决（P0 RSS 搜索已涉及网络请求）
- **Drawbacks**：增加开发成本；缓解措施：复用现有网络安全组件

#### 7.2.2 ADR-020 性能预算策略

- **Status**：Proposed
- **Context**：54 项任务完成后 APK 体积、启动时间、内存占用可能显著增长。ADR-016 定义了性能基准测试方法学但未定义性能预算上限。ADR-004 仅约束 UI 优化类包体积增长 ≤ 5MB 但未覆盖整体 APK 体积上限。
- **Decision**：
  1. **APK 体积上限**：整体 APK 体积 ≤ 当前 + 10MB（含 UI 优化 5MB + 其他 5MB）
  2. **启动时间上限**：冷启动时间 ≤ 当前 + 10%
  3. **内存占用上限**：峰值内存 ≤ 当前 + 50MB
  4. **FPS 下限**：阅读翻页 FPS ≥ 50，视频播放 FPS ≥ 30
  5. **搜索响应上限**：RSS 搜索 < 3s（5 源并发）
- **Consequences**：
  - 正向：性能可量化可对比、避免性能退化、为优化提供目标
  - 负向：部分借鉴点可能因性能预算无法实施
- **Alternatives**：
  - 备选 A：不设性能预算 → 否决（性能退化无法及时发现）
  - 备选 B：仅设 APK 体积上限 → 否决（启动时间/内存同样重要）
- **Drawbacks**：部分借鉴点可能因预算无法实施；缓解措施：超预算时优先保留高用户价值项

#### 7.2.3 ADR-021 错误处理与异常上报统一策略

- **Status**：Proposed
- **Context**：ADR-015 协程调度策略仅覆盖协程错误处理（Coroutine.onError）。缺少业务异常分类、用户提示策略、异常上报策略的统一说明。54 项任务中多项可能产生业务异常（如 RSS 搜索失败、视频加载失败、EPUB 解析失败、主题包导入失败等）。
- **Decision**：
  1. **异常分类**：业务异常（NoStackTraceException 子类）+ 网络异常 + IO 异常 + 数据库异常
  2. **用户提示**：可恢复异常显示 Toast，不可恢复异常显示 Dialog 并提供重试选项
  3. **异常上报**：异常通过 AppLog.put() 记录到本地日志，禁止上报到第三方服务（隐私保护）
  4. **异常隔离**：单源/单文件/单章节失败不影响整体功能，错误信息收集后统一展示
  5. **回退策略**：关键功能（如 EPUB 渲染）失败时回退到简化模式
- **Consequences**：
  - 正向：用户体验一致、异常可追踪、不影响整体功能
  - 负向：增加异常处理代码量
- **Alternatives**：
  - 备选 A：不统一错误处理 → 否决（用户体验不一致，难以排查问题）
  - 备选 B：使用第三方异常上报服务 → 否决（违反隐私保护原则）
- **Drawbacks**：增加异常处理代码量；缓解措施：建立异常处理工具类

#### 7.2.4 ADR-022 兼容性策略

- **Status**：Proposed
- **Context**：项目 minSdk 已提升至 23，但部分新增依赖可能要求 API 24+。如 rhino 1.8.1 锁定原因之一是 API 24 以下缺少 Arrays.setAll。liquidglass 1.0.3、lottie 6.6.6 等新增依赖的 minSdk 兼容性未明确。
- **Decision**：
  1. **minSdk 锁定**：minSdk 23 不变，所有新增依赖必须支持 API 23+
  2. **API 级别检查**：使用 @RequiresApi 注解 + 运行时版本判断
  3. **屏幕适配**：所有新增 UI 适配 4.5-10 寸屏幕，支持横竖屏
  4. **依赖兼容性验证**：新增依赖引入前必须验证 minSdk 兼容性
- **Consequences**：
  - 正向：保证低版本设备兼容性、避免崩溃
  - 负向：部分新特性无法使用
- **Alternatives**：
  - 备选 A：提升 minSdk 至 24 → 否决（影响现有用户）
  - 备选 B：不验证依赖兼容性 → 否决（运行时崩溃风险）
- **Drawbacks**：部分新特性无法使用；缓解措施：使用降级方案

#### 7.2.5 ADR-023 日志策略

- **Status**：Proposed
- **Context**：ADR-015 仅说明了"异常用 Coroutine.onError 捕获后用 AppLog.put() 记录"。但日志级别、日志保留策略、日志上报策略、用户隐私保护未明确。项目规范 logging-during-refactoring.md 要求"改造过程日志记录"但缺乏统一日志策略。
- **Decision**：
  1. **日志级别**：DEBUG（开发期）/ INFO（关键流程）/ WARN（异常可恢复）/ ERROR（异常不可恢复）
  2. **日志工具**：统一使用 AppLog.put()，禁止 android.util.Log.d/e
  3. **日志保留**：本地日志保留 7 天，超期自动清理
  4. **日志脱敏**：禁止记录完整 URL、cookie、token、用户密码等敏感信息
  5. **日志上报**：仅本地存储，禁止自动上报到第三方服务
- **Consequences**：
  - 正向：日志规范统一、便于排查问题、保护用户隐私
  - 负向：增加日志管理代码
- **Alternatives**：
  - 备选 A：使用 Timber → 否决（项目规范明确禁止）
  - 备选 B：不统一日志策略 → 否决（日志泛滥，难以排查）
- **Drawbacks**：增加日志管理代码；缓解措施：建立日志工具类

#### 7.2.6 ADR-024 测试覆盖率策略

- **Status**：Proposed
- **Context**：ADR-012 仅说明真机测试强制流程，未定义单元测试覆盖率要求。ADR-016 仅说明性能基准测试，未定义功能测试覆盖率。54 项任务中新增多个工具类（如 PaperInkHelper、VideoBookPreloader、SearchBookMergeUtils 等），需明确单元测试覆盖率要求。
- **Decision**：
  1. **单元测试覆盖率**：新增工具类单元测试覆盖率 ≥ 80%
  2. **集成测试**：每个模块至少 1 个集成测试场景
  3. **真机测试**：每个 P 阶段完成后必须真机测试（已在 ADR-012 约束）
  4. **回归测试**：P2 完成后全量回归测试
  5. **测试工具**：JUnit + Mockito + ai_tests/scripts/
- **Consequences**：
  - 正向：代码质量有保证、问题早发现
  - 负向：增加测试开发工作量
- **Alternatives**：
  - 备选 A：不要求覆盖率 → 否决（无法保证测试质量）
  - 备选 B：覆盖率 ≥ 95% → 否决（成本过高，部分 UI 代码难以测试）
- **Drawbacks**：增加测试开发工作量；缓解措施：优先测试核心业务逻辑

#### 7.2.7 ADR-025 发布策略

- **Status**：Proposed
- **Context**：54 项任务分三阶段实施，但未定义版本号管理、灰度发布、回滚策略。ADR-011 仅说明文档同步，未说明版本号与发布流程。
- **Decision**：
  1. **版本号**：采用语义化版本号（Major.Minor.Patch），P0/P1/P2 各对应一个 Minor 版本
  2. **灰度发布**：每个版本先内部测试 → 灰度 10% → 灰度 50% → 全量
  3. **回滚策略**：每个版本发布后保留回滚能力（保留旧版本 APK）
  4. **发布渠道**：GitHub Release + Gitee 镜像同步
  5. **发布前检查**：编译通过 + 真机测试通过 + 文档同步 + 性能基准达标
- **Consequences**：
  - 正向：版本演进可追踪、问题可回滚、用户体验稳定
  - 负向：增加发布管理工作量
- **Alternatives**：
  - 备选 A：不灰度直接全量发布 → 否决（问题影响所有用户）
  - 备选 B：不保留回滚能力 → 否决（问题无法快速恢复）
- **Drawbacks**：增加发布管理工作量；缓解措施：使用 CI 自动化发布

## 10. 分析结论

### 10.1 总体评估

18 个 ADR 整体质量较高，Y-Statement 字段齐全、决策合理、备选充分。存在以下需改进点：

1. **ADR-010 建议拆分**：主题导入导出与云端同步差异显著，拆分后可更清晰约束

5. **1 个低可行性 ADR**：ADR-010 主题包云端同步部分实施成本高、风险大，建议拆分后单独评估
