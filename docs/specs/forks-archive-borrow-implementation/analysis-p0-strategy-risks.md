## 2. P0 实施策略深度分析

### 2.1 当前 P0 分组方案评估

> **v5.1 调整说明（2026-07-18）**：本节基于 v5.0 版本 P0 分组方案进行评估，当时 P0 分组含 13 项任务（10 纯 P0 + 3 项混入 P1：RSS-B-05/THEME-B-03/VIDEO-B-02）。**v5.1 调整后 P0=14（10 纯 P0 + 4 升级 P1→P0：RSS-B-05/VIDEO-B-02/VIDEO-E-01/VIDEO-E-02）**，THEME-B-03 保持 P1 不升级。本节 §2.1.1 分组回顾保留 v5.0 基线以供追溯，实际实施以 v5.1 调整后 P0=14 为准（与 README/spec/tasks/design 一致）。

#### 2.1.1 当前分组方案回顾

来自 design.md §6.1 与 ADR-002（v5.0 基线，P0 分组含 13 项任务：10 纯 P0 + 3 项混入 P1）：

```
组1（RSS 主线，组内串行，预计 3-4 人天）
  ├─ RSS-B-05 (RssFragment 入口，P1) → RSS-B-01 (RssSearchActivity)
  ├─ RSS-B-02 (SourceSelectDialog)
  ├─ RSS-B-03 (SearchBookMergeUtils)
  └─ RSS-E-06 (cacheFirst 默认值)

组2（THEME 视觉，组内并行，预计 2-3 人天）
  ├─ THEME-B-01 (纸墨风格 PaperInkHelper.kt)
  ├─ THEME-B-02 (字体撞色检测 ThemeColorUtils.kt)
  └─ THEME-B-03 (主题包 ZIP，P1)

组3（EPUB 加速，组内串行，预计 1-2 人天）
  ├─ EPUB-B-01 (章节资源索引 spine 优先 EpubFile.kt)
  └─ EPUB-B-02 (资源过滤+标题归一化 EpubFile.kt)

组4（VIDEO 预加载，组内串行，预计 1-2 人天）
  ├─ VIDEO-B-01 (VideoBookPreloader)
  ├─ VIDEO-B-02 (预加载集成，P1)
  └─ DEPS-B-01 (markwon 扩展，独立)
```

> **v5.1 调整后 P0 分组（14 项）**：剔除 THEME-B-03（保持 P1），新增 VIDEO-E-01/VIDEO-E-02 升级 P0，RSS-B-05/VIDEO-B-02 正式纳入 P0。详见 README §5.1 Phase 1 P0 任务明细（14 项）。

#### 2.1.2 分组合理性评估

**评估维度 1：按模块分组（合理）**
- 4 个组对应 4 个独立模块（RSS / THEME / EPUB / VIDEO+DEPS）
- 模块间耦合度低，符合"文件隔离原则"
- DEPS-B-01 独立性强，可附挂任意组

**评估维度 2：按依赖分组（部分合理）**
- 组 3 内 EPUB-B-01 → EPUB-B-02 依赖识别正确（共用 `EpubFile.kt`）
- 组 1 内 RSS-B-05 → RSS-B-01 依赖识别正确（共用 `RssFragment.kt`）
- ⚠️ **隐藏依赖未识别**：RSS-B-03 需要集成到 `SearchActivity.kt`，与 RSS-B-01 的搜索流程可能存在隐性耦合
- ⚠️ **隐藏依赖未识别**：RSS-B-02 `SourceSelectDialog` 弹出的源列表可能与 RSS-B-01 搜索流程共用源数据源

**评估维度 3：按工作量分组（极不均衡）**

基于 tasks.md §1 明示工作量重新统计：

| 组 | 任务 | 工作量（人天） | 小计 |
|----|------|--------------|------|
| 组1 | RSS-B-05(0.5) + RSS-B-01(1-2) + RSS-B-02(2) + RSS-B-03(2) + RSS-E-06(0.5) | 6-7 | **6-7** |
| 组2 | THEME-B-01(1) + THEME-B-02(1) + THEME-B-03(P1未明示，估1-2) | 3-4 | **3-4** |
| 组3 | EPUB-B-01(0.5) + EPUB-B-02(1) | 1.5 | **1.5** |
| 组4 | VIDEO-B-01(1) + VIDEO-B-02(P1未明示，估1) + DEPS-B-01(0.5) | 2.5 | **2.5** |
| **合计** | - | - | **13-15** |

**关键问题**：
- 设计文档 ADR-002 声称"工期从 10-15 人天缩短至 6-10 人天"，但实际汇总为 13-15 人天
- spec.md §3.1 声称"实际工作量约 10.5-11.5 天"，与 design.md 矛盾
- 组 1 工作量是组 3 的 4 倍，**严重不均衡**
- 若 4 组真并行，组 3 完成后需等待组 1 完成（约 4.5 天空窗）

#### 2.1.3 隐藏依赖深度分析

**隐藏依赖 1：RssFragment.kt 文件冲突**
- RSS-B-01 子任务 1.1.4："RssFragment 添加搜索入口（5 行代码）"
- RSS-B-05 子任务 2.1.1.1："RssFragment 添加 openRssSearch 方法"
- 两者都修改 `app/src/main/java/io/legado/app/ui/rss/RssFragment.kt`
- 当前分组将 RSS-B-05 → RSS-B-01 串行处理，符合"同文件串行"规范
- 但 RSS-B-05 是 P1 任务，不应在 P0 启动

**隐藏依赖 2：SearchActivity.kt 隐性耦合**
- RSS-B-03 子任务 1.8.3："集成到搜索界面（SearchActivity）"
- design.md §4.6 文件清单第 3 项：`SearchActivity.kt` 修改关联 RSS-B-03 + RSS-E-05
- 但 RSS-B-01 的 `RssSearchActivity` 是否继承 `BaseSearchActivity`？若是，则与 `SearchActivity` 共用父类
- 这种隐性耦合未在分组中体现

**隐藏依赖 3：源数据共用**
- RSS-B-01 `RssSearchViewModel` 调度多源并发搜索 → 需要 RssSource 列表
- RSS-B-02 `SourceSelectDialog` 展示 book/rss 源 → 也需要 RssSource 列表
- 两者数据源相同，若同时实施可能引入数据加载顺序问题

**隐藏依赖 4：build.gradle 单点修改**
- DEPS-B-01 修改 `app/build.gradle`（添加 markwon 扩展依赖）
- 任何其他组如果也涉及 build.gradle 修改（如新增 res 配置），将冲突
- 当前 P0 中仅 DEPS-B-01 涉及 build.gradle，无冲突

**隐藏依赖 5：strings.xml 资源共用**
- ADR-018 要求所有新增字符串放入 strings.xml
- 4 组新增的字符串都在同一文件 `app/src/main/res/values/strings.xml`
- 这是组间隐藏冲突点，需协调

#### 2.1.4 是否有更优分组方案

**结论：当前分组方案存在可优化空间**

主要问题：
1. P0 中混入 3 项 P1 任务（详见 §2.1.5）
2. 工作量极不均衡（组 1 是组 3 的 4 倍）
3. 组 1 内部 RSS-B-02 / RSS-B-03 与 RSS-B-01 无强依赖，不应强制串行
4. 组 2 中 THEME-B-03 是 P1 任务，不应在 P0 启动

### 2.2 替代分组方案探索

#### 2.2.1 方案 B：按用户场景分组

| 组 | 场景 | 任务 | 优点 | 缺点 |
|----|------|------|------|------|
| 组A | 看书场景 | EPUB-B-01 + EPUB-B-02 + THEME-B-01 | 用户感知一致 | 跨模块协调难 |
| 组B | 订阅场景 | RSS-B-01 + RSS-B-02 + RSS-B-03 + RSS-E-06 | 同模块内聚 | 工作量过重 |
| 组C | 视频场景 | VIDEO-B-01 + DEPS-B-01 | 同入口 | DEPS 与视频无场景关联 |
| 组D | 主题场景 | THEME-B-02 | 独立 | 工作量过轻 |

**评估**：未解决工作量不均衡问题，反而加剧。

#### 2.2.2 方案 C：按技术栈分组

| 组 | 技术栈 | 任务 | 优点 | 缺点 |
|----|--------|------|------|------|
| 组A | UI 层 | RSS-B-01 + RSS-B-02 + THEME-B-01 + THEME-B-02 | 同层抽象 | 跨模块文件冲突 |
| 组B | 数据/业务层 | RSS-B-03 + RSS-E-06 | 数据处理统一 | 工作量过轻 |

**评估**：跨模块文件冲突风险高，不推荐。

#### 2.2.3 方案 D：按风险等级分组

| 组 | 风险等级 | 任务 | 优点 | 缺点 |
|----|---------|------|------|------|
| 组A | 低风险（独立新增） | THEME-B-01 + THEME-B-02 + VIDEO-B-01 + DEPS-B-01 | 风险隔离 | 工作量过重 |
| 组B | 中风险（修改现有） | RSS-B-01 + RSS-B-02 + RSS-B-03 | 风险统一管理 | 跨模块文件冲突 |
| 组C | 性能相关 | EPUB-B-01 + EPUB-B-02 + RSS-E-06 | 性能基准统一 | 跨模块文件冲突 |

**评估**：跨模块文件冲突严重，不推荐。

#### 2.2.4 方案 E：纯 P0 严格分组（推荐）

**核心原则**：严格遵守 P0 定义，剔除所有 P1 任务

| 组 | 任务 | 工作量（人天） | 文件隔离 |
|----|------|--------------|---------|
| 组A（RSS 主线） | RSS-B-01 + RSS-B-02 + RSS-B-03 + RSS-E-06 | 5.5-6 | RSS 模块内 |
| 组B（THEME 视觉） | THEME-B-01 + THEME-B-02 | 2 | THEME 模块内 |
| 组C（EPUB 加速） | EPUB-B-01 + EPUB-B-02 | 1.5 | EPUB 模块内 |
| 组D（VIDEO+DEPS） | VIDEO-B-01 + DEPS-B-01 | 1.5 | VIDEO+DEPS 模块内 |
| **合计** | 10 项纯 P0 任务 | 10.5-11 | - |

**优点**：
- 严格遵守 P0 定义（10 项任务），不混入 P1
- 工作量较均衡（组 A 6 天 vs 组 C 1.5 天，比 4:1 改善至 4:1）
- 文件隔离清晰，无跨组冲突
- 与 spec.md §3.1 "10.5-11.5 天" 估算一致

**缺点**：
- 组 A 工作量仍是最重，但可通过组内并行缓解（RSS-B-02/03 与 RSS-B-01 无强文件依赖）

#### 2.2.5 方案 F：组内并行优化版

在方案 E 基础上，对组 A 内部进一步并行化：

```
组A（RSS 主线，组内并行）：
  ├─ 串行链：RSS-B-01 (RssSearchActivity + RssFragment 入口)
  ├─ 并行1：RSS-B-02 (SourceSelectDialog，独立文件)
  ├─ 并行2：RSS-B-03 (SearchBookMergeUtils，独立文件)
  └─ 并行3：RSS-E-06 (cacheFirst 默认值，独立修改)
```

**工作量优化**：
- 串行链 RSS-B-01：1-2 天
- 并行 3 项同时进行：max(2, 2, 0.5) = 2 天
- 组 A 总工作量：1-2 + 2 = 3-4 天（比原 6 天缩短 33%）

### 2.4 P0 工期估算验证

#### 2.4.1 当前估算矛盾分析

| 来源 | 估算 | 依据 |
|------|------|------|
| design.md ADR-002 | 6-10 人天 | "工期从 10-15 人天缩短至 6-10 人天（缩短约 30%）" |
| design.md §6.1 | 3-4 + 2-3 + 1-2 + 1-2 = 7-11 人天 | 各组工作量明示 |
| spec.md §3.1 | 10.5-11.5 天 | "实际工作量约 10.5-11.5 天，2 周窗口充裕" |
| tasks.md §1 | RSS(6) + THEME(2-3) + EPUB(1.5) + VIDEO(2.5) = 12-13 天 | 各任务明示工作量 |

**关键矛盾**：
- design.md 内部矛盾：ADR-002 说 6-10 人天，§6.1 各组汇总为 7-11 人天
- design.md vs spec.md：6-10 vs 10.5-11.5
- design.md vs tasks.md：6-10 vs 12-13

#### 2.4.2 估算依据充分性评估

**已考虑因素**：
- ✅ 代码编写工作量（tasks.md 明示）
- ✅ 真机测试工作量（每项任务都有"真机验证"子项）

**未考虑因素**：
- ❌ **代码理解成本**：需理解 Archive 项目原实现（RssSearchActivity 104 行 / VideoBookPreloader 90 行 / PaperInkHelper 60 行）
- ❌ **调试成本**：首次集成新代码通常有调试时间（估 20-30% 工作量）
- ❌ **文档同步成本**：updateLog.md / tasks.md / project_memory.md / forks-reference.md / INDEX.md 五份文档同步
- ❌ **返工成本**：真机测试发现问题后的返工（估 10-20% 工作量）
- ❌ **strings.xml 国际化成本**：ADR-018 要求所有新增字符串入 strings.xml，多语言版本
- ❌ **单元测试编写成本**：tasks.md 明示多项单元测试覆盖
- ❌ **性能基线建立成本**：ADR-016 要求 P0 前建立基线（估 1-2 人天）
- ❌ **协调沟通成本**：4 组并行需主 Agent 协调（估 0.5-1 人天）

#### 2.4.3 建议的工期估算

**纯 P0 任务（10 项）工期估算**：

| 阶段 | 工作内容 | 工作量（人天） |
|------|---------|--------------|
| 1. P0 前置准备 | 性能基线建立 + 单元测试环境准备 + Archive 原实现理解 | 1.5-2 |
| 2. 代码编写 | 10 项 P0 任务编码（按 tasks.md 明示工作量） | 10.5-11 |
| 3. 调试 | 20-30% 调试时间 | 2-3 |
| 4. 真机测试 | 每项任务真机验证 + 问题修复 | 1.5-2 |
| 5. 文档同步 | updateLog + tasks + project_memory + forks-reference + INDEX | 0.5-1 |
| 6. 协调沟通 | 主 Agent 协调 4 组进度 + 组间合并校验 | 0.5-1 |
| 7. 返工缓冲 | 10-20% 返工 | 1.5-2.5 |
| **合计** | - | **18-22.5** |

**关键结论**：
- 当前 6-10 人天估算**严重低估**，实际应在 **18-22 人天**
- 2 周窗口（10 工作日）**不足**，建议扩展至 **3-4 周**
- 若坚持 2 周窗口，需削减 P0 范围或允许延期

**建议工期**：
- **保守估算**：22 人天 ≈ 4-5 周
- **乐观估算**：18 人天 ≈ 3-4 周
- **激进估算**：15 人天 ≈ 3 周（需削减部分任务或允许部分测试延后）
