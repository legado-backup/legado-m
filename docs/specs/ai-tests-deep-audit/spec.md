# spec.md — ai_tests 深度审计与补全完善

## Intent

对 `ai_tests/` 自动化测试基础设施进行全面审计，系统性识别：
1. 当前架构的优点（值得保留和推广的设计）
2. 当前存在的缺点（代码异味、架构缺陷、质量问题）
3. 缺失项（未实现功能、空壳模块、文档缺口）
4. 需要补全完善的具体方案

## Scope

### In Scope（本次审计范围）

- **lib/ 10 模块**：M1-M9 + feedback_loop 的实现完整性
- **scripts/ 150+ 脚本**：分类统计、临时脚本识别、质量评估
- **tests/ 10 单元测试**：覆盖率、有效性分析
- **run_e2e.py 编排层**：V3 功能实现状态、降级逻辑
- **config.py 固化层**：常量完整性和准确性
- **docs/ 8 文档**：完整性、时效性、一致性
- **cases/ 用例**：覆盖模块和场景完整性
- **架构一致性**：README 描述 vs 实际实现
- **依赖管理**：requirements.txt vs 实际使用

### Out of Scope（不在本次范围）

- 重写整个 ai_tests 框架
- 实现所有缺失功能（仅识别+规划，实施另开任务）
- 性能压测
- 安全审计

## Approach

### Selected Approach：分层审计法

按 Layer 0-3 四层架构逐层审计，每层从"实现完整性 → 代码质量 → 测试覆盖 → 文档一致性"四个维度评估。

理由：
- ai_tests 自身就是分层架构（Layer 0-3），分层审计最自然
- 四维度评估覆盖了"能否运行 → 运行质量 → 质量保障 → 使用体验"全链路
- 识别出的缺失项可直接映射到对应 Layer 和维度，便于后续补全

### Alternatives Considered

| 方案 | 描述 | 否决理由 |
|------|------|---------|
| 单维度横切法 | 按"代码质量/测试/文档"维度横切所有模块 | 丢失了架构层级间的依赖关系，不利于定位根因 |
| 自动化扫描工具 | 用 pylint/pytest-cov 等工具自动扫描 | 工具只能发现语法/覆盖率问题，无法识别架构缺陷和空壳模块 |
| 逐文件遍历法 | 逐个读取所有文件做分析 | 150+ 脚本逐文件分析效率极低，且缺乏结构化视角 |

### Drawbacks

- 分层审计依赖人工判断"空壳"vs"未完成"，可能误判
- 脚本数量多（150+），不可能逐一深度分析，需按分类抽样
- 审计结果反映当前快照，不追踪历史演进

### Prior Art

- 项目已有 `docs/specs/e2e-automated-testing/` 设计文档，可作为 V3 设计基线对照
- `docs/project-rules/ai_e2e_testing_workflow.md` 定义了 E2E 测试工作流

## Requirements

### R1：优点识别
- 系统性列出 ai_tests 的架构优点和设计亮点
- 每个优点需有具体代码/设计证据支撑

### R2：缺点识别
- 识别代码异味、架构缺陷、质量问题
- 识别临时/冗余脚本
- 识别硬编码、路径耦合等问题
- 每个缺点需说明影响范围和严重程度

### R3：缺失项识别
- 识别空壳模块（有文件但无实质实现）
- 识别 V3 设计中声明但未实现的功能
- 识别测试覆盖缺口
- 识别文档与实现不一致

### R4：补全方案
- 针对每个缺点和缺失项，给出优先级排序的补全方案
- 方案需可执行（有明确的实施步骤和验证标准）
- 区分"短期止损"和"长期完善"

### R5：产出物
- 生成结构化审计报告（含优点/缺点/缺失/方案四部分）
- 报告需可被后续 OpenSpec 任务直接引用

## Scenarios

### S1：空壳模块识别
- **Given** lib/ 下有 10 个模块文件
- **When** 逐模块检查实现完整性
- **Then** 识别出 source_test_generator.py / feedback_loop.py / source_impact_analyzer.py 等空壳模块

### S2：临时脚本统计
- **Given** scripts/ 下有 150+ 脚本
- **When** 按命名模式分类（temp_* / v5_* / _v5*_* / 正式脚本）
- **Then** 统计临时脚本数量和占比，识别可清理项

### S3：V3 功能实现状态
- **Given** README 声明了 V3 双轨调度、--diff、--gen-test、--feedback
- **When** 对照 run_e2e.py 和 lib/ 实际实现
- **Then** 列出每个 V3 功能的实现状态（已实现/降级/空壳/未实现）

### S4：测试覆盖率
- **Given** tests/ 下有 10 个测试文件
- **When** 对照 lib/ 10 个模块
- **Then** 识别哪些模块有测试、哪些没有、测试质量如何

### S5：依赖审计
- **Given** requirements.txt 列出 7 个依赖
- **When** 检查实际 import 使用情况
- **Then** 识别未使用的依赖和缺失的依赖
