# Design：子代理编排与思考预算优化

## Technical Approach

### 核心架构：主代理-子代理分层调度

```
┌─────────────────────────────────────────┐
│  主代理（Main Agent）                    │
│  - 调度与协调                            │
│  - 用户交互（AskUserQuestion）           │
│  - 源码文件串行修改                      │
│  - 子代理产出二次验证                    │
│  - 工具调用预算：≤30 次/对话            │
├─────────────────────────────────────────┤
│  子代理（Sub-Agent）× N                  │
│  - 独立工具调用预算                      │
│  - 独立思考 token 预算                   │
│  - 独立上下文窗口                        │
│  - 职责：分析/文档生成/深度探索          │
│  - 禁止：修改源码文件                    │
│  - 产出：结构化结果+完成级别声明         │
└─────────────────────────────────────────┘
```

### 职责分层

| 层级 | 执行者 | 职责 | 工具调用预算 |
|------|--------|------|------------|
| **调度层** | 主代理 | 任务拆解、子代理启动、监控、验证、用户交互 | ≤30 次/对话 |
| **执行层** | 子代理 | 文件分析、文档生成、深度探索、代码搜索 | 独立预算（不计入主对话） |
| **源码修改层** | 主代理 | 源码文件 Edit（串行化，遵守并发规范） | 计入主对话预算 |

### 关键设计决策

1. **子代理只做分析/文档，不修改源码**——解决与"并发文件修改规范"的冲突
2. **同步模式优先**——OpenSpec 顺序流程需要子代理结果才能继续
3. **主代理二次验证**——不信任单一来源，所有子代理产出必须验证
4. **禁止建议新对话**——新对话收费，优先"继续"+子代理分担

## Architecture Decisions

### AD-01：子代理作为"对话内虚拟新对话"
- **Context**：GLM-5.2 在 Trae 平台有"思考次数上限"（工具调用轮次+思考 token+上下文累积），频繁触发导致任务中断
- **Concern**：如何在不增加成本（不开新对话）的前提下，最大化同对话内的工作量？
- **Decision**：强制使用子代理执行大任务，子代理有独立预算且不额外收费
- **Goal**：在同对话内扩展工作量，避免触发思考上限，避免新对话
- **Tradeoff**：接受子代理调用的额外开销（启动+prompt 传递），换取避免触发上限和新对话的更大成本
- **Status**：Proposed

### AD-02：子代理禁止修改源码文件
- **Context**：AGENTS.md "并发文件修改规范"要求"源码文件修改串行化，禁止委托给后台 Agent 触碰同一源码文件"
- **Concern**：强制子代理与并发文件修改规范有冲突
- **Decision**：子代理只做分析/文档任务，源码修改由主代理串行执行
- **Goal**：既利用子代理扩展工作量，又遵守并发文件修改规范
- **Tradeoff**：源码修改仍在主对话消耗预算，但通过子代理分担分析工作，间接减少主对话总消耗
- **Status**：Proposed

### AD-03：降低子代理触发阈值
- **Context**：AGENTS.md 现有"复杂任务处理流程"触发阈值是 50+源文件，过高
- **Concern**：50+文件阈值下，大多数任务仍由主代理直接执行，无法规避思考上限
- **Decision**：降低触发阈值为 ≥5 文件 / ≥10 工具调用 / 深度分析任务
- **Goal**：让更多任务走子代理路径，降低主对话触发思考上限的概率
- **Tradeoff**：更多任务走子代理路径，增加子代理调用开销；但远小于触发上限的成本
- **Status**：Proposed

### AD-04：禁止以"避免思考上限"为由建议新对话
- **Context**：新对话收费，一次新对话一次钱
- **Concern**：V2 方案曾建议"任务拆分到多次对话"，这会直接增加成本
- **Decision**：禁止建议新对话，触发上限时优先"继续"+子代理分担
- **Goal**：避免增加用户成本
- **Tradeoff**：同对话内上下文会累积，可能影响后期质量；但通过子代理分担和 /compact 缓解
- **Status**：Proposed

### AD-05：主代理二次验证子代理产出
- **Context**：子代理产出可能不合格（空壳代码/遗漏关键内容/逻辑错误）
- **Concern**：如何保证子代理完成任务的质量？
- **Decision**：主代理收到子代理结果后必须二次验证（Read/Grep/编译/功能检查）
- **Goal**：确保子代理产出可靠性 ≥ 95%
- **Tradeoff**：二次验证消耗主对话预算（少量工具调用）；但不验证会导致质量问题，返工成本更高
- **Status**：Proposed

### AD-06：同步模式优先
- **Context**：子代理支持同步（run_in_background: false）和异步（true）两种模式
- **Concern**：OpenSpec 顺序流程需要子代理结果才能继续后续工作
- **Decision**：默认使用同步模式，主代理等待子代理完成；异步模式仅用于独立后台任务
- **Goal**：保证 OpenSpec 流程的顺序性和可预测性
- **Tradeoff**：同步模式会阻塞主代理，但保证了流程正确性
- **Status**：Proposed

### AD-07：子代理 prompt 标准化
- **Context**：子代理产出质量高度依赖 prompt 清晰度
- **Concern**：如何确保子代理理解任务并产出符合期望的结果？
- **Decision**：子代理 prompt 必须包含四要素：任务描述+输入清单+期望输出格式+验证标准
- **Goal**：提升子代理首次执行的成功率，减少重试
- **Tradeoff**：标准化 prompt 增加少量编写成本；但减少重试和验证成本
- **Status**：Proposed

### AD-08：分级子代理策略（低风险强制，高风险禁止）
- **Context**：原方案"强制子代理"过于激进，对高风险任务（架构决策/源码修改）会降低质量；子代理存在上下文割裂风险
- **Concern**：如何在规避思考上限的同时保证输出质量？
- **Decision**：按任务风险分级——低风险（文档/分析）强制子代理；中风险（实施分析）推荐子代理；高风险（决策/源码修改/用户交互）禁止子代理，主代理直接执行
- **Goal**：既规避思考上限，又保证高风险任务的质量
- **Tradeoff**：高风险任务仍在主对话消耗预算，但通过子代理分担低风险任务，间接减少总消耗
- **Status**：Proposed

### AD-09：实验性标注与兜底机制
- **Context**：子代理是否真的有独立预算无法 100% 确认；方案有效性存在不确定性
- **Concern**：如果方案无效或降低质量怎么办？
- **Decision**：规范标注为"实验性 V1"，保留兜底（"继续"优先，子代理是补充）；如果无效或降质，及时调整
- **Goal**：可控的实验，避免一刀切导致质量下降
- **Tradeoff**：实验性标注可能让 AI 不严格执行；但通过"低风险强制"保证核心场景执行
- **Status**：Proposed

## Data Flow

### 流程1：OpenSpec 步骤2（生成四文档）

```
主代理
  │
  ├─ 1. 需求分析（主代理直接执行，≤3次工具调用）
  │     - Grep 搜索相关代码
  │     - Read 读取关键文件片段
  │
  ├─ 2. 启动子代理生成四文档
  │     - Agent(prompt=四文档需求+输入+输出格式+验证标准)
  │     - 子代理独立执行：
  │       - 子代理 Grep/Read 探索代码
  │       - 子代理 Write 四个文档
  │       - 子代理返回"已生成四文档，路径 xxx"
  │
  ├─ 3. 主代理验证（≤5次工具调用）
  │     - Read 确认四文件存在
  │     - Grep 确认关键章节存在（如 spec.md 的 Alternatives Considered）
  │
  └─ 4. 检查点1（主代理直接执行）
        - AskUserQuestion 汇报"已生成四文档"
        - 正文只给摘要，不输出文档内容
```

**主对话工具调用预算**：≤10 次（远低于触发阈值）

### 流程2：OpenSpec 步骤5（实施）

```
主代理
  │
  ├─ 1. 启动子代理分析相关代码（每个任务）
  │     - Agent(prompt=分析 xxx 模块的 yyy 功能)
  │     - 子代理返回结构化分析报告
  │
  ├─ 2. 主代理基于分析串行修改源码
  │     - Edit 文件A（串行）
  │     - Edit 文件B（串行）
  │     - 遵守并发文件修改规范
  │
  ├─ 3. 主代理验证（每完成3个任务）
  │     - Grep 确认变更存在
  │     - 编译验证
  │     - /compact（主动压缩上下文）
  │
  └─ 4. 检查点2（主代理直接执行）
        - AskUserQuestion 汇报进度
```

### 流程3：触发思考上限后的恢复

```
主代理
  │
  ├─ 1. 触发"思考次数上限"
  │     - Trae 显示提示
  │     - 用户输入"继续"
  │
  ├─ 2. 主代理识别已触发上限
  │     - 后续工作改为子代理执行
  │     - 主代理只做调度和验证
  │
  └─ 3. 子代理分担后续工作
        - 大任务委托子代理
        - 主对话工具调用降到最低
```

## 验证策略

### 阶段1：文件层验证（当前可做）
- 四文档完整性检查（必须章节齐全）
- AGENTS.md 修改后语法正确
- 子规范文件创建成功

### 阶段2：加载层验证（需新对话）
- 新对话中 AI 是否加载了更新后的规范
- 通过 AI 输出"已加载的项目主规范"验证清单确认

### 阶段3：行为层验证（需实际任务）
- 下次执行 OpenSpec 任务时，AI 是否按新规范使用子代理
- 主对话工具调用次数是否减少
- 是否避免触发思考上限
