# 改造过程日志记录规范（logging-during-refactoring）

> **任何代码优化、改造、Bug 修复任务，在实施过程中必须适度添加日志，帮助定位分析问题、发现隐藏问题、避免遗漏问题。**
>
> 本规范是对 `project_memory.md` P0 规则23（复杂功能实施必须添加临时日志验证）的升级：从"临时日志验证"升级为"改造过程中必须加日志"的永久规范。
>
> **来源**：用户反馈（2026-07-12）——AI 在改造代码时必须适度添加日志，帮助定位分析问题、发现隐藏问题、避免遗漏问题

## 核心原则

| 原则 | 说明 |
|------|------|
| **改造必加日志** | 任何代码改造（优化/Bug修复/新功能）必须在关键路径添加日志 |
| **适度而非过度** | 日志要精准覆盖关键路径，避免日志洪水（影响性能/难以筛选） |
| **永久+临时双轨** | 永久日志（错误处理/状态切换）保留；临时日志（调试验证）验证后移除 |
| **日志即文档** | 日志内容应能反推代码逻辑，便于后续维护者理解流程 |
| **问题不遗漏** | 通过日志覆盖所有错误分支，确保隐藏问题能被发现 |

## 日志添加的合理必要性分析

### 必须加日志的 10 类场景

| # | 场景 | 必要性 | 日志内容 | 级别 |
|---|------|--------|---------|------|
| 1 | **播放器状态切换** | 降级/播放/暂停/释放等状态转换需可追踪 | 前状态→后状态+触发原因+URL路径模式 | `Log.d` |
| 2 | **错误处理路径** | 所有 catch 块和错误码处理必须记录 | 异常类型+错误码+关键参数+调用栈关键帧 | `AppLog.put` |
| 3 | **网络请求关键节点** | 请求发起/成功/失败/重试需可追踪 | URL路径模式（不含查询参数）+响应码+耗时 | `Log.d`/`AppLog.put` |
| 4 | **数据库异常** | 查询失败/记录跳过/超大记录需记录 | 表名+操作类型+异常类型+记录位置 | `AppLog.put` |
| 5 | **类型转换** | String→List/JSON解析等类型处理 | 原类型→目标类型+转换结果（成功/失败） | `Log.d` |
| 6 | **加密解密** | 解密失败/数据长度异常需记录 | 源名称+算法+异常类型+数据长度 | `AppLog.put` |
| 7 | **生命周期关键节点** | Fragment/WebView/Player 创建/销毁 | 组件名+操作+hashCode（便于追踪实例） | `Log.d` |
| 8 | **配置变更** | 播放器类型切换/设置变更需可追踪 | 配置项+前值→后值+触发来源 | `Log.d` |
| 9 | **触摸事件流转** | 事件分发/消费/穿透需可追踪（复杂UI场景） | 事件类型+目标View+消费结果 | `Log.d` |
| 10 | **JS 交互** | JS调用Native/Native调用JS需可追踪 | 方法名+参数摘要（过滤敏感）+返回结果 | `Log.d` |

### 不需要加日志的场景

| 场景 | 原因 |
|------|------|
| 简单 getter/setter | 无逻辑分支，日志无价值 |
| 常规 UI 渲染（非状态切换） | 高频调用，日志洪水 |
| 循环体内常规迭代 | 高频调用，性能影响 |
| 已有日志覆盖的路径 | 避免重复日志 |

## 日志级别与使用场景

### AppLog.put（永久日志，面向用户/开发者）

```kotlin
// 使用场景：错误处理、异常捕获、用户可感知的问题
AppLog.put("视频播放失败", "url: ${urlPathOnly}, 错误码: ${errorCode}, 异常: ${exception.javaClass.simpleName}", error)
```

**适用场景**：
- 所有 `catch` 块
- 错误码处理（如 ExoPlayer 的 `onPlayerError`）
- 用户可感知的功能失败（播放失败/加载失败/解密失败）
- 数据库异常

### Log.d（调试日志，面向开发者）

```kotlin
// 使用场景：状态追踪、流程验证、参数记录
Log.d("VideoPlay", "降级到WebView: url=${urlPathOnly}, title=${title}, reason=${reason}")
```

**适用场景**：
- 状态切换追踪
- 流程时序验证
- 参数传递检查
- 生命周期事件

## Tag 命名规范

| Tag 模式 | 适用场景 | 示例 |
|----------|---------|------|
| 模块名 | 永久日志 | `VideoPlay` / `ExoPlayer` / `RssParse` |
| 模块名+功能 | 临时调试日志 | `SwipeTest` / `WebViewDegradation` / `TouchTrace` |

**临时日志 Tag 规范**：
- 使用统一的功能性 Tag（如 `SwipeTest`），便于验证后一次性移除
- 禁止用随机字符串（如 `abc123`），无法 grep 定位

## 日志内容规范

### 必须记录的信息

| 信息类型 | 说明 | 示例 |
|---------|------|------|
| **操作/事件** | 发生了什么 | `降级到WebView` / `解密失败` / `Fragment销毁` |
| **关键参数** | 涉及的参数（过滤敏感） | `url=/path/{id}`（不含查询参数） / `position=3` / `sourceName=站点A` |
| **状态转换** | 前→后 | `GSY→WebView` / `playing→paused` |
| **触发原因** | 为什么发生 | `reason=ERROR_CODE_IO_UNSPECIFIED` / `cause=UnrecognizedInputFormatException` |
| **异常类型** | 异常类名+错误码 | `IllegalBlockSizeException` / `errorCode=2000` |

### 禁止输出的信息（输出安全规范）

| 禁止项 | 处理方式 | 原因 |
|--------|---------|------|
| 完整 URL（含查询参数） | 只保留路径模式 `/path/{id}` | 含 token/key 等敏感参数 |
| 视频/影视网站域名 | 用代号（站点A/B/C） | 避免触发审查机制 |
| token/cookie/password/key | 完全隐藏 `***` | 敏感字段 |
| 原始日志/HTML 全文 | 提取关键技术信息 | 日志洪水+可能含敏感信息 |
| 视频内容描述 | 只保留技术结构 | 避免触发审查机制 |

## 临时日志 vs 永久日志

### 永久日志（保留）

| 特征 | 说明 |
|------|------|
| 覆盖错误处理路径 | 所有 catch/错误码分支 |
| 覆盖状态切换 | 播放器类型/播放状态/生命周期 |
| 使用 AppLog.put | 写入应用日志文件，用户可查看 |
| 不移除 | 作为代码的永久部分保留 |

### 临时日志（验证后移除）

| 特征 | 说明 |
|------|------|
| 用于验证特定功能 | 如滑动切换/触摸事件/时序依赖 |
| 使用统一功能 Tag | 如 `SwipeTest` / `DegradationTest` |
| 使用 Log.d | 不写入应用日志文件，仅 logcat |
| 验证通过后移除 | Grep Tag 一次性删除所有相关日志 |

### 临时日志使用流程（适用于多组件交互/时序依赖/事件流转等复杂场景）

```
1. 实施复杂功能（涉及多组件交互/时序依赖/事件流转）
2. 在关键路径添加 Log.d（统一 Tag 如 "SwipeTest"）
3. 编译 → 安装 → 操作 → logcat 抓取
4. 分析日志：确认各关键路径被正确调用、参数正确、时序正确
5. 发现问题 → 修复 → 重新验证
6. 验证通过 → Grep Tag 一次性移除所有临时日志
7. 重新编译确认无残留
```

## 反模式

❌ 改造代码不加日志，事后无法定位问题根因
❌ 日志内容包含完整 URL / 视频/影视域名 / 敏感字段
❌ 临时日志不统一 Tag，无法一次性移除
❌ 验证通过后不移除临时日志，污染代码
❌ 日志过于详细（循环体内/高频调用），导致日志洪水
❌ 错误处理路径只有 catch 没有 AppLog.put，异常被静默吞掉
❌ 日志只记录"失败"不记录"原因"，无法定位根因
❌ 状态切换只记录"切换后"不记录"切换前+触发原因"，无法追踪流程
❌ 永久日志用 Log.d（不写入文件），用户反馈问题时无法查看
❌ 临时日志用 AppLog.put（写入文件），污染用户日志

## 验证检查清单

改造任务完成前，逐项核对：

- [ ] 所有 catch 块是否有 AppLog.put（含异常类型+关键参数）？
- [ ] 所有错误码处理分支是否有日志（含错误码+建议操作）？
- [ ] 所有状态切换是否有日志（前→后+触发原因）？
- [ ] 复杂功能（多组件交互/时序依赖）是否添加了临时 Log.d？
- [ ] 临时日志是否使用统一 Tag？
- [ ] 日志内容是否过滤了敏感字段（URL查询参数/域名/token）？
- [ ] 验证通过后是否移除了所有临时日志（Grep Tag 确认）？
- [ ] 重新编译是否确认无临时日志残留？

## 调试日志清理（强制）

> **代码变更任务完成前，必须扫描并清理所有临时调试日志。**

### 清理时机

- 功能验证通过后立即清理临时调试日志
- 任务交付前必须确认无调试日志残留
- 编译安装前必须执行清理检查

### 清理方法

```bash
# Grep 搜索所有临时调试日志（排除 AppLog.put 永久日志）
# 使用 Grep 工具，pattern: android\.util\.Log\.(d|e|w|i)，type: kt
```

### 临时日志识别

| 类型 | 特征 | 处理 |
|------|------|------|
| 临时调试日志 | tag为功能名（LoginRefresh/LoginCookie/CronetCookie等） | 移除 |
| 永久错误日志 | AppLog.put | 保留 |
| 永久状态日志 | Log.d + 模块名tag（VideoPlay/ExoPlayer等） | 保留 |

### 反模式

- ❌ 临时调试日志残留到交付版本（本次清理12处残留，用户批评"别再被我测试发现问题"）
- ❌ 只清理部分文件，遗漏其他文件
- ❌ 清理后不重新编译验证
- ❌ 清理后不移除未使用的TAG常量定义
