# 子代理质量管理与监控规范

> **版本**：V1 实验性
> **创建日期**：2026-07-12
> **适用范围**：所有使用子代理（Agent 工具）的任务
> **关联规范**：[AGENTS.md](../../AGENTS.md) "复杂任务处理流程"、"并发文件修改规范"

## 1. 背景与目标

当前模型在 Trae 平台有"思考次数上限"（工具调用轮次+思考 token+上下文累积）。子代理有独立预算且不额外收费，是"对话内的虚拟新对话"。但子代理存在**上下文割裂**和**产出质量**风险，本规范定义监控与质量保证机制。

**目标**：在规避思考上限的同时，保证子代理产出可靠性 ≥ 95%。

## 2. 分级子代理策略

### 2.1 低风险任务（✅ 强制子代理）

| 任务类型 | 示例 | 理由 |
|---------|------|------|
| 文档生成 | OpenSpec 四文档/分析报告 | 质量风险低，主代理验证关键章节即可 |
| 代码分析 | 源码探索/架构分析/Grep+Read 搜索 | 子代理返回结构化报告，主代理决策 |
| 大文件读取 | 单文件 > 500 行 | 避免占用主对话上下文 |
| OpenSpec 步骤2 | 生成四文档 | 并行生成，主代理只验证 |

### 2.2 中风险任务（🟡 推荐子代理）

| 任务类型 | 示例 | 策略 |
|---------|------|------|
| 实施阶段分析 | OpenSpec 步骤5 Grep/Read 探索 | 子代理分析，主代理基于结果修改源码 |
| 多文件探索 | ≥ 5 个源文件 | 子代理返回汇总，主代理决策 |

### 2.3 高风险任务（❌ 禁止子代理，主代理直接执行）

| 任务类型 | 理由 |
|---------|------|
| 架构决策/方案选择 | 需要用户偏好和上下文，子代理会割裂 |
| 源码文件修改（Edit） | 遵守并发文件修改规范，质量可控 |
| 用户交互（AskUserQuestion） | 子代理不与用户交互 |
| 需要用户反馈的深度分析 | 上下文割裂风险高 |

## 3. 子代理 prompt 标准化（四要素）

子代理 prompt **必须**包含以下四要素，缺一不可：

### 3.1 任务描述
- 明确的任务目标（做什么）
- 任务边界（不做什么）
- 完成标准（什么算完成）

### 3.2 输入清单
- 相关文件路径（绝对路径）
- 相关规范引用（AGENTS.md 路径+章节）
- 用户偏好摘要（lazy principle/AskUserQuestion/输出安全等）
- 用户反馈摘要（若有，当前任务相关的关键反馈）

### 3.3 期望输出格式
- 结构化输出模板（如 Markdown 表格/JSON）
- 必须包含的章节
- 完成级别声明（Level 1/2/3）
- 潜在问题说明

### 3.4 验证标准
- 主代理将如何验证产出
- 必须包含的关键内容
- 禁止的内容（如空壳代码/占位符）

### 3.5 prompt 模板示例

```
任务：分析 {模块名} 的 {功能} 实现

输入：
- 文件路径：{绝对路径}
- 规范引用：AGENTS.md "{章节名}"
- 用户偏好：lazy principle（全生命周期效率，非省略验证）/ 必须用 AskUserQuestion / 输出安全（不输出完整URL/敏感字段）
- 用户反馈：{当前任务相关的关键反馈摘要}

输出格式：
- 结构化分析报告（Markdown）
- 必须包含：①当前实现方式 ②潜在问题 ③改进建议 ④完成级别（Level 1/2/3）

验证标准：
- 主代理将 Read 确认分析覆盖所有文件
- 必须包含上述4个章节
- 禁止空壳分析（每章节至少3行实质内容）
```

## 4. 主代理监控机制

### 4.1 同步模式（默认）

```
主代理 → Agent(run_in_background: false) → 等待 → 收到结果
```

- **适用**：OpenSpec 顺序流程、需要子代理结果才能继续的任务
- **优点**：流程可预测，主代理立即收到结果
- **缺点**：主代理阻塞等待

### 4.2 异步模式（仅限独立后台任务）

```
主代理 → Agent(run_in_background: true) → 继续其他工作 → 收到完成通知
```

- **适用**：文档同步、独立分析任务
- **优点**：主代理不阻塞
- **缺点**：需要 TaskOutput 查询结果

### 4.3 监控工具

| 工具 | 用途 | 使用场景 |
|------|------|---------|
| `TaskOutput` | 查询子代理输出 | 异步模式查询结果，`block=true` 等待完成 |
| `SendMessage` | 向子代理发送补充指令 | 子代理产出不全/需补充信息 |
| `TaskStop` | 停止子代理 | 子代理失控/方向错误 |

## 5. 主代理二次验证（强制）

### 5.1 验证清单

主代理收到子代理结果后，**必须**按以下清单验证：

| 产出类型 | 验证方式 | 通过标准 |
|---------|---------|---------|
| 新增文件 | Read 确认文件存在 + 关键代码段存在 | 文件存在 + 关键章节/函数存在 |
| 修改文件 | Grep 确认变更内容确实存在 | 变更内容存在 |
| 代码编译 | 运行编译命令 | 编译无错误 |
| 功能实现 | Grep+Read 确认函数签名 + 逻辑非空壳 | 函数存在 + 逻辑非空 |
| 文档生成 | Read 确认必须章节存在 | 必须章节齐全 |
| 分析报告 | Read 确认结构完整 + 关键结论存在 | 结构完整 + 结论非空 |

### 5.2 验证失败处理

```
验证失败
  ├─ 轻微问题（遗漏少量内容）→ SendMessage 补充指令 → 子代理修正
  ├─ 严重问题（方向错误/空壳）→ 重新启动子代理（修订 prompt）
  └─ 多次失败（≥2次）→ 主代理直接执行（放弃子代理）
```

### 5.3 完成级别声明

子代理产出必须声明完成级别：

| 级别 | 含义 | 验证要求 |
|------|------|---------|
| Level 1 - 代码完成 | 文件存在 + 编译通过 | Read + 编译验证 |
| Level 2 - 功能验证 | 关键功能可运行 + 输出正确 | Grep+Read 逻辑验证 |
| Level 3 - 场景验证 | 真实数据回测通过 | 实际运行验证 |

## 6. 失败重试策略

### 6.1 重试决策

| 失败类型 | 重试次数 | 策略 |
|---------|---------|------|
| 轻微遗漏 | 1 次 | SendMessage 补充指令 |
| 方向偏差 | 1 次 | 重新启动子代理（修订 prompt） |
| 多次失败 | ≥2 次 | 主代理直接执行 |
| 子代理触发上限 | 1 次 | 主代理直接执行（任务粒度太大） |

### 6.2 重试 prompt 优化

每次重试时，prompt 必须包含：
- 上次失败原因
- 本次调整内容
- 更明确的完成标准

## 7. 与现有规范的协调

### 7.1 与"并发文件修改规范"的协调

- **冲突**：并发文件修改规范要求"源码文件修改串行化，禁止委托给后台 Agent"
- **解决**：子代理**禁止修改源码文件**；子代理只做分析/文档；源码修改由主代理串行执行

### 7.2 与"复杂任务处理流程"的协调

- **调整**：触发阈值从 50+文件 降低到 5+文件或10+工具调用（低风险任务）
- **保留**：≤12 文件/子代理上限、同批次全部并行、必须交叉验证
- **边界说明**：5+ 文件或 10+ 工具调用=子代理分级低风险阈值；50+ 文件=五阶段流水线硬约束，两者作用对象不同（前者决定是否/如何启用子代理，后者决定是否强制走 complex-task-pipeline 五阶段流程）

### 7.3 与 OpenSpec 工作流程的协调

- **步骤2**：生成四文档改为子代理并行生成
- **步骤5**：实施阶段分析用子代理，源码修改由主代理串行
- **检查点**：仍由主代理直接执行（AskUserQuestion）

### 7.4 与 core-spec 交互规范的协调

- **规则**：子代理不直接与用户交互
- **执行**：所有 AskUserQuestion 由主代理发起

## 8. 兜底机制

### 8.1 触发思考上限后的处理

```
触发"思考次数上限"
  ├─ 第1步：用户输入"继续"续接
  ├─ 第2步：主代理识别已触发，后续工作改为子代理执行
  ├─ 第3步：主代理只做调度和验证，不再直接执行大任务
  └─ 第4步：如果子代理也触发（说明预算不独立），调整为"减少输出+/compact"策略
```

### 8.2 实验性标注

- 本规范为 V1 实验性
- 首次使用时观察效果
- 如果无效或降质，及时调整：
  - 子代理也触发上限 → 收紧使用范围，更多任务主代理直接执行
  - 质量下降 → 收紧高风险任务范围
  - 效果良好 → 扩大低风险强制范围

## 9. 反模式

❌ 子代理修改源码文件（违反并发文件修改规范）
❌ 子代理直接与用户交互（违反 core-spec 交互规范）
❌ 主代理不验证子代理产出（违反质量保证）
❌ 子代理 prompt 缺少四要素（任务/输入/输出/验证）
❌ 以"避免思考上限"为由建议用户新开对话（新对话收费）
❌ 高风险任务委托子代理（架构决策/源码修改）
❌ 子代理产出不声明完成级别
❌ 验证失败不重试直接接受
